# 主题配色 —— 依八字喜用而定

> 本文是 UI 配色与 Logo 的**唯一依据**。改配色前先读这份文档，改完后同步更新。
> 色值由 `tools/build-palette.mjs` 生成与校验（含 WCAG AA 与「色相归位」两项检查）。
>
> **2026-09 重大更正**：初版把日柱记成了甲子、日主当成甲木，据此把火定为用神。
> 核对儒略日后日柱应为**丙寅**、日主是**丙火** —— 喜用整体改变，
> 主色系从「火土」改为「**木火**」，整套色板重做。更正说明见附录。

## 一、命局

**出生**：公历 1985 年 1 月 27 日 23:15　吉林市船营区（东经 126.56°、北纬 43.84°）

### 真太阳时修正

出生地经度与「北京时间」所依据的标准经线（120°E）不一致，必须修正：

| 项 | 修正量 | 依据 |
|---|---|---|
| 经度时差 | **+26.2 分** | 126.56°E 相对 120°E 偏东 6.56 度 × 4 分钟/度 |
| 均时差 | **−12.3 分** | 地球轨道偏心率与黄赤交角，1 月下旬约为 −12 至 −13 分 |
| 夏令时补偿 | 0 分 | 中国仅 1986–1991 年夏季实行过夏令时，1985 年不涉及 |
| **合计** | **+14.0 分** | |

**钟表时间 23:15 → 真太阳时 23:28**，仍属子时。

> 这一步不能省。经度修正量随出生地变化极大：喀什（75.99°E）是 **−176 分**，
> 也就是钟表时间要往回拨近 3 小时 —— 不做修正会直接算错时辰，而时辰错了时柱就错。

### 四柱推算过程

| 柱 | 结果 | 推算依据 |
|---|---|---|
| 年柱 | **甲子** | 1985 年立春在 2 月 4 日 15:25（北京时间），出生时刻在其**前**，年柱仍用上一年干支 → 1984 = 甲子年。★ 年柱以**立春**为界，不是正月初一 |
| 月柱 | **丁丑** | 小寒（1/5 09:33）至立春（2/4 15:25）为丑月；甲年五虎遁「甲己之年丙作首」，寅月起丙寅，顺推至丑月得丁丑 |
| 日柱 | **丙寅** | 儒略日 **JDN(1985-01-27) = 2446093**；干支序 = (JDN + 49) mod 60 = 2；索引 2 = 丙寅 |
| 时柱 | **戊子** | 真太阳时 23:28 属子时（23:00–00:59）；日干**丙**，五鼠遁「丙辛从戊起」→ 戊子 |

关于 JDN 的交叉验证：1949-10-01 的 JDN = 2433191，该日干支为**甲子日**（公论），
用同一公式回推 1985-01-27 得丙寅，与万年历一致。

### 四柱

              年        月        日        时
天干          甲        丁        丙        戊
地支          子        丑        寅        子
十神          偏印      劫财      日主      食神

### 格局

**丙火日主生于丑月（腊月），隆冬寒火。**

- **水旺寒凝**：年支子、时支子，冬水本旺，直接克丙火
- **土泄火**：月支丑为湿土（冬土），火生土而耗力；时干戊土亦泄
- **木为生源**：日支**寅**藏甲木（本气）与丙火（中气），是全局唯一的生火之源
- **一点丁火**：月干丁火劫财本可助身，但坐丑土泄之，力弱

合参：**寒火向阳、非木不生**之象。病在寒湿，药在温暖；而温暖的来源只能是木 ——
没有木，火就无从谈起。这一点是初版（甲木日主）与更正后（丙火日主）结论不同的关键。

### 关于子时日界

23:15 落在**当日**子时之内，按默认口径（日在子正，00:00 换日）日柱不换日。

若按「子时换日」口径（23:00 起即进次日）：日柱 **丁卯**、时柱 **庚子**。

两种口径的喜用结论一致（都需木火），故配色结论对流派选择**不敏感** ——
这正是把两派结果都展示出来的意义：让用户看到差异，也看到差异不影响结论。

## 二、喜用

| | 五行 | 理由 |
|---|---|---|
| **用神** | **木** | 丙火生腊月，天寒地冻，非木不生。木既生火，又能化水（水生木、木生火，把克火的水转成生火的木） |
| **喜神** | **火** | 木生火、火暖局，日主得助。丙火得比助则不畏寒 |
| **闲神** | **土** | 火生土而泄火之力；但土能制水，功过相抵，只作点缀 |
| **忌神** | **水** | 冬水本旺，再增则直接克火，日主受制 |
| **忌神** | **金** | 金生水而助寒；且金克木 —— 木是用神，克木即断火之源，双重不利 |

### 大运

甲子年、阳年、男命 → 大运**顺行**。生于 1985-01-27，顺数至惊蛰（1985-03-05）约 37 天，约 12 岁起运：

```
戊寅(约1997) → 己卯 → 庚辰 → 辛巳 → 壬午 → 癸未 → 甲申 → 乙酉
```

戊寅、己卯两步（土、木）得力 —— 寅中甲木正是用神；
庚辰之后金水渐重，宜以木火调之，与喜用结论一致。

## 三、配色策略：低饱和 · 商用质感

初版采用高饱和中式配色（主色 `#d95a2b`，饱和 70%），视觉偏「文化感」而非「企业软件」。
改版确定三条原则：

### ① 骨架中性

中性色一律取**近真灰**（饱和 ≤8%），不带色相。

这是商用质感的关键 —— 界面主体必须「无色」。低饱和色一旦用在背景与文字上，
整屏会泛棕泛黄，立刻显旧。所以五行意象只放在**点**上，不放在**面**上。

### ② 颜色克制

主色（木）饱和 30%、辅色（火）24%、点缀（土）20%，全板强调色不超过 **31%**。

**五行意象由「色相」承载，不由「饱和度」堆**：

| 五行 | 色相区间 | 初版（高饱和） | 现版 |
|---|---|---|---|
| 木 | 70–170 度 松绿 | `#4a7c3f` 饱和 33% | `#376754` 饱和 30%（**主色**） |
| 火 | 0–45 度 赤陶 | `#d95a2b` 饱和 70% | `#966a5c` 饱和 24%（辅色） |
| 土 | 45–70 度 赭黄 | `#b8802a` 饱和 63% | `#847b58` 饱和 20%（点缀） |

低饱和的松绿依然是木 —— 不需要靠高饱和去「证明」。

> **色相区间与判定区间必须对齐**：`hueToElement()` 把 45–70° 判为土，
> 那么土系色板的实际色相就必须落在 45–70°。初版土系用的是 36°（偏橙），
> 界面上一边标「这个色属于土」，一边在算占比时把它算成火，用户看到的结论自相矛盾。
> 这是 `build-palette.mjs` 里加「色相归位校验」的原因。

### ③ 可读性优先

所有承载文字的色均过 **WCAG AA（不小于 4.5:1）**，由 `tools/build-palette.mjs` 逐项校验。

## 六、外观偏好页：填入自己的出生信息

`/appearance` 页不是普通取色器。页面顶部先让人把**出生信息**填对，
再由系统算出四柱与喜用，最后才轮到调色 —— 顺序反映因果：**配色是喜用的结果**。

> ★ **这一段只属于外观偏好页，不进入登录首页。**
>   登录页可能被别人看到，把命盘摆在首屏是不必要的暴露；
>   而且在那一屏要回答的是"这软件靠不靠得住"，不是"它按谁的八字配色"。
>   所以登录页只呈现品牌名、一句话与三条产品承诺，
>   装饰取中式的留白与纹样（山云、钤印、回纹角饰），不取内容。
>
>   下方第一节那组四柱是**内置默认色板所依据的示例**（一例寒月丙火），
>   不是"本系统实控人"的命盘 —— 任何人都可以在偏好页填入自己的信息覆盖它。

### 输入项

| 项 | 说明 |
|---|---|
| 历法 | 公历 / 农历（含闰月标记）。农历会先转公历再推算 —— 八字建立在**节气**上，与月相无关 |
| 出生日期与时刻 | 按 24 小时制填**钟表时间**，不必自己换算真太阳时 |
| 出生地 | 62 个地级市预置（`packages/shared/src/bazi/cities.ts`）+「手工填经纬度」兜底 |
| 真太阳时 | 可关。关掉时界面会警示（时柱可能整整差一个时辰） |
| 子时日界 | 「日在子正」/「日在子初」二选一，**另一种口径的结果同时列出** |

出生地只到地级市是有意的：经度修正按 4 分钟/度算，同一地级市内经度差通常不足 0.5 度
（< 2 分钟），对一个 120 分钟的时辰几乎没有影响。真需要逐分钟精确的，
用「手工填经纬度」—— 那个入口必须留，预置表无论多长都不够用。

### 展示内容

- **真太阳时修正明细**：经度时差 / 均时差 / 夏令时补偿 / 合计，四段分开列。
  把 `+14 分` 是怎么来的摆出来，用户才能判断「为什么这里算的和我手机上那个 App 不一样」，
  而不是把差异当成 bug。
- **四柱 + 十神**、**五行本气分布**（悬停看含藏干的加权值）
- **边界警示**：离节气或时辰边界很近时提示可能翻转。默认示例真太阳时 23:28，
  距子时边界 32 分钟，界面会明确标出来
- **另一种子时口径的结果**、**推算口径与依据**（可折叠，逐步列出怎么算的）

### 调色方向提示

调色方向由后端的 `ELEMENT_ROLE` 表推导（`GET /preferences/theme/tokens` 的 `guidance`），
前端不硬写五行。原因很实际：改一次喜用要找齐所有出现过「火土」的字符串，必然漏，
而漏掉的那处会继续给用户**错误的调色建议** —— 比不提示更糟。

## 七、全局偏好（可持久化）

配色不是硬编码，而是**可由用户调整并跨会话生效的全局偏好**。

### 存储与层级

存在 `SystemConfig` 表，key = `ui.theme`。读取优先级：

```
主体级配置（entityId = 某主体）
    ↓ 未命中
全局配置（entityId = NULL）
    ↓ 未命中
代码内置默认（依八字喜用）
```

因为「界面长什么样」是**人的偏好**而非账套属性，所以真正的默认值放全局，
主体级只作可选覆盖。

### 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/preferences/theme?entityId=` | 读取配置 + 五行分布分析 + 命局说明 |
| `GET` | `/api/preferences/theme/tokens` | 令牌元数据 + 喜忌角色 + 色相区间 + 调色指引 |
| `PATCH` | `/api/preferences/theme` | 局部更新（只提交改动的色） |
| `POST` | `/api/preferences/theme/reset` | 恢复默认 |

### 前端

`apps/web/src/stores/preferences.ts` 把颜色写进 `:root` 的 CSS 变量，两级缓存：

1. **localStorage** —— 页面启动时**先于网络请求**应用，避免刷新闪默认色
2. **后端为准** —— 拉取成功后覆盖本地，保证多设备一致

### 五行分布分析

`analyzeElementBalance()` 做三件事：

**① 令牌归属统计** —— 木火（喜用）占比。低于 45% 会提示加强。

**② 实际色相校验** —— 逐令牌比对色值的**色相**是否偏离应有五行。

第 ② 条是后补的，因为踩过坑：把主色改成蓝色 `#5f7695`，
第一版检测却是「无警告」—— 它只看令牌名叫 `fire500`，没看里面填的是什么色。
修正后的判定表：

| 色相区间 | 判定五行 |
|---|---|
| 0–45 度 / 330–360 度 | 火 |
| 45–70 度 | 土 |
| 70–170 度 | 木 |
| 170–330 度 | **水（忌神）** |

饱和度低于 12% 的视为中性（灰阶），不参与判定。
相邻色相（火↔土、土↔木）不算冲突，视觉上可接受。

**③ 角色文案全部由 `ELEMENT_ROLE` 推导** —— 包括告警与结论措辞。
硬写五行名的话，改喜用必然漏掉某处，而漏掉的那处会继续给错误建议。

## 八、实现约束

1. **颜色一律走 CSS 变量**，组件里不写死色值。

2. **引入顺序不能变**（`apps/web/src/main.ts`）：

   ```
   element-plus/dist/index.css -> styles/theme.css -> styles/global.css
   ```

   `theme.css` 必须在 Element Plus 默认样式**之后**，否则 `:root` 变量会被默认值压掉。

3. **Element Plus 组件级变量要显式映射**。
   只覆盖 `--el-color-primary` 不够：按钮、tag 等组件内部还有
   `--el-button-*` / `--el-tag-*` 一层局部变量，不一定回退到全局主题色。
   特别是 `is-text` / `is-plain` 变体，需要把 hover 背景与文字色**整组**给到，
   否则会出现「主按钮是主题色，但文字按钮 hover 时变回默认蓝」。

4. **禁用态也要中性灰**。Element Plus 默认禁用态是冷灰蓝（`#a0cfff` 一类），
   在低饱和主题里很突兀。

5. 自定义属性必须在 `:root` 下声明 —— 写在 `.el-button` 这类选择器里的
   自定义属性**不会**级联到子元素。

6. **全局配置（entityId = null）不能用 Prisma `upsert`**：
   复合唯一键的 `where` 不接受 `null`，且 PostgreSQL 中 NULL 互不相等、
   唯一索引拦不住重复行。必须 `findFirst + update/create`，并清理历史重复行。

7. **加令牌要三处同步**：`COLOR_TOKEN_KEYS`（领域模型）、`TOKEN_META`（设置页元数据）、
   `theme.css`（默认色值）。`wood` 从点缀升为主色时，就因为它只有 3 个令牌、
   撑不起一条主色阶，才补齐成 8 个（50/100/200/300/400/500/600/700）。

## 附录：2026-09 更正说明

### 错在哪

初版按「甲子年 丁丑月 **甲子日** 甲子时、日主甲木」推算，把火定为用神。
两处错误：

| 项 | 错值 | 正确值 | 原因 |
|---|---|---|---|
| 日柱 | 甲子 | **丙寅** | 文档记 JDN(1985-01-27) = 2446097，实际是 **2446093**（差 4 天） |
| 时柱 | 甲子 | **戊子** | 日干错成甲，五鼠遁「甲己还加甲」自然错；丙日应为「丙辛从戊起」 |

年柱 甲子、月柱 丁丑**原本正确**。

### 怎么发现的

用儒略日公式独立复算，并与公认锚点交叉验证：1949-10-01 的 JDN = 2433191，
该日干支为甲子日（无争议）。以它为基准回推 1985-01-27，得丙寅，与万年历一致；
而 2446097 对应的是 1985-01-31。

### 影响

日主由甲木变为丙火，喜用**整体改变**：

| | 初版（甲木日主） | 更正后（丙火日主） |
|---|---|---|
| 用神 | 火 | **木** |
| 喜神 | 土 | **火** |
| 闲神 | 木 | **土** |
| 忌神 | 水、金 | 水、金（不变） |

主色系从「火土」改为「**木火**」：角色表整体前移一格，色板重做。
忌神不变，所以「避开黑、深蓝、冷银」这条约束从头到尾都成立 ——
界面骨架的中性方向无需调整。

### 教训

**推算过程要留可复算的中间值。** 初版文档只写了结论（甲子日），
没写 JDN 的具体数值是怎么参与运算的，所以错误藏了很久 ——
年柱月柱都对，看起来不像有问题的样子。现在文档把 JDN 数值、
干支序公式、交叉验证锚点都写出来了，任何人可以两分钟复算一遍。

配套地，`packages/shared/src/bazi` 里的推算全部返回 `methodology` 数组，
界面必须把它展示出来（默认折叠）—— 结论和过程一起给，才可能被独立核对。
