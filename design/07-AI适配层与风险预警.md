# 07 · AI 适配层与风险预警

## 1. AI 在本系统里的三个用途（以及边界）

| 用途 | 输入 | 输出 | 出错后果 | 允许自动执行？ |
|---|---|---|---|---|
| **识图抽取** | 发票/回单/合同图片 | 结构化字段 + 置信度 | 字段错 → 由交叉校验拦截 | 抽取可自动；**入账必须过校验** |
| **科目建议** | 票据 + 历史凭证 | 科目 + 借贷方向 + 理由 | 记错科目 | ✗ 永远只是建议，人工确认 |
| **风险预警** | 账套数据摘要 | 异常清单 + 解释 | 漏报/误报 | ✓ 只读分析，不影响数据 |

**共同边界（写进代码，不写进提示词）**

1. AI **永远不能**决定金额。金额一律由系统按模板与票据字段计算，AI 只选科目与方向。
2. AI 输出**必须**通过 Schema 校验 + 会计交叉校验，才允许进入下一步。
3. AI 建议**永不允许**自动过账（`autoPost` 对 AI 来源强制为 `false`）。
4. AI 的每一次输出都写 `AiCallLog`，包含 prompt 版本、模型、原始响应、耗时、成本。
   **任何一张凭证都能反查到"当时 AI 说了什么"。**

## 2. Provider 适配层

```
                    ┌──────────────────────────────┐
                    │  AiProvider (interface)       │
                    │  · chat()      文本          │
                    │  · vision()    多模态         │
                    │  · ping()      健康检查       │
                    │  · estimateCost()             │
                    └───────────┬──────────────────┘
                                │
   ┌────────────┬───────────────┼───────────────┬─────────────────┐
   ▼            ▼               ▼               ▼                 ▼
MockProvider  OpenAiCompat   QwenVlProvider  LocalProvider   （未来）
开发/测试      ★ 主力          （可选）        Ollama/vLLM      票据专用OCR API
离线可用      一个适配器       独立实现        数据不出内网
              覆盖 90%        便于用特有参数
```

### 接口定义

```ts
export interface AiProvider {
  readonly name: string;

  ping(): Promise<{ ok: boolean; models?: string[]; message?: string }>;

  chat(req: ChatRequest): Promise<ChatResponse>;

  vision(req: VisionRequest): Promise<ChatResponse>;

  estimateCost(req: ChatRequest | VisionRequest): Promise<Decimal | null>;
}

export interface ChatRequest {
  system: string;
  messages: Array<{ role: 'user' | 'assistant'; content: string }>;
  temperature?: number;          // 记账场景默认 0
  maxTokens?: number;
  jsonMode?: boolean;            // 要求返回严格 JSON
  timeoutMs?: number;
  purpose: AiPurpose;
  entityId?: string;
  documentId?: string;
}

export interface VisionRequest extends Omit<ChatRequest, 'messages'> {
  images: Array<{ path?: string; base64?: string; mimeType: string }>;
  text?: string;                 // 伴随图片的文本指令或 PDF 文本层
  promptKey: string;
  promptVersion: string;
}

export interface ChatResponse {
  text: string;
  json?: unknown;                // jsonMode 且解析成功时填充
  usage?: { promptTokens: number; completionTokens: number };
  model: string;
  latencyMs: number;
  raw: unknown;
}
```

### 为什么只写一个 `OpenAiCompatProvider` 就够

DeepSeek、通义千问 VL、豆包、智谱 GLM-4V、Moonshot、以及 vLLM/Ollama 自建模型，
都提供 OpenAI 兼容的 `/v1/chat/completions`（含 `image_url` 多模态入参）。
差异只在 `baseUrl`、`model` 名、以及个别参数（如是否支持 `response_format: json_object`）。

因此设计：**一个 Provider + 能力探测 + 参数降级**

```
能力探测（首次调用时缓存）:
  · 请求 response_format=json_object
    → 400/不支持 → 降级为"提示词强制 JSON + 后处理提取"
  · 请求多图输入
    → 失败 → 降级为逐图单独调用后合并
```

```bash
# 换成通义千问 VL
AI_PROVIDER=openai-compatible
AI_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
AI_VISION_MODEL=qwen-vl-max
AI_TEXT_MODEL=qwen-plus

# 换成自建本地模型（数据不出内网）
AI_PROVIDER=openai-compatible
AI_BASE_URL=http://host.docker.internal:11434/v1
AI_VISION_MODEL=qwen2.5-vl:7b
AI_API_KEY=ollama

# 开发：零成本、离线、结果确定
AI_PROVIDER=mock
```

## 3. Mock Provider：开发体验的关键

`MockOcrProvider` 不是玩具，它决定了**开发阶段是否会被 API 成本卡住**。

```ts
// 行为
// 1. 按文件名/内容哈希稳定映射到一个样例 fixtures
//    invoice-special-vat-1300.json / invoice-red-flush.json / bank-slip-in.json ...
// 2. 返回固定的结构化数据与置信度
// 3. 每个样例都能覆盖至少一条校验规则（含故意触发 V4 购销方颠倒的样例）
// 4. 支持通过文件名后缀指定样例：__case=red-flush
```

好处：
- 新人 clone 下来 `AI_PROVIDER=mock` 就能把全链路（导入→识图→规则→凭证→结账→报表）跑通。
- CI 里跑端到端测试不花钱、不抖动。
- 校验规则、规则引擎、报表都能被真实数据形状测试到。

## 4. 提示词工程规范

### 4.1 版本化存储

```
packages/prompts/
├── invoice-extract@v1.md
├── invoice-extract@v2.md          ← 改了就新增版本，不原地改
├── bank-slip-extract@v1.md
├── bank-statement-extract@v1.md
├── contract-extract@v1.md
├── account-suggest@v1.md
└── anomaly-explain@v1.md
```

- 每次调用记录 `promptKey` + `promptVersion` 到 `AiCallLog`。
- 改提示词 → 版本 +1 → 可用 `AiCallLog` 对比新旧版本的纠错率。
- **禁止原地修改已上线版本的提示词**（否则历史记录无法解释）。

### 4.2 提示词结构模板

```markdown
# 角色
你是中国增值税发票信息抽取引擎。

# 任务
从图片中抽取发票字段，严格按 JSON Schema 输出。

# 硬性规则
1. 只输出 JSON，不要 Markdown 代码块，不要任何解释文字。
2. 金额只输出数字，不带千分位、不带货币符号。¥1,234.56 → 1234.56
3. 严格按票面文字识别。看不清的字段输出 null，**不要猜测、不要补全**。
4. 大写金额与小写金额不一致时，以大写为准，并在 _warnings 中说明。
5. 购买方名称为「{{entityName}}」（税号 {{entityTaxNo}}）时 direction="INPUT"；
   销售方为该名称时 direction="OUTPUT"；都不是则 direction=null 并在 _warnings 说明。

# 输出 Schema
{{schema}}

# 票面文本（若为电子发票，优先以此为准，图片仅作校验）
{{textLayer}}

# 字段置信度
对每个字段给出 0~1 的置信度，放在 _fieldConfidence 中。
```

### 4.3 提升准确率的实用做法

| 做法 | 效果 |
|---|---|
| 把本主体名称+税号写进提示词，让模型判方向 | 显著降低购销方颠倒（V4 类错误） |
| PDF 优先用文本层，图片仅作校验 | 省 token，且电子发票准确率接近 100% |
| 提示词里放大写金额的核对规则 | 拦金额数字错误 |
| `temperature = 0` | 结果可复现，便于回归测试 |
| 要求输出 `_fieldConfidence` 与 `_warnings` | 让模型"表达不确定"，而不是硬编 |
| few-shot 给 2~3 个真实样例（含一个红字票） | 版式适配能力强很多 |
| 长提示词放前缀，图片放后面 | 提高前缀缓存命中率（省成本） |

## 5. 风险预警体系

### 5.1 双通道设计

```
┌─ 确定性规则（SQL / 领域逻辑）────────────────────────────┐
│  优点：准确、可解释、零成本、可写成测试用例                 │
│  覆盖：80% 的已知风险模式                                 │
│  执行：月结时（S10）+ 每日定时                            │
└────────────────────┬─────────────────────────────────────┘
                     │
┌────────────────────▼─────────────────────────────────────┐
│  AI 异常检测（可选，按需开启）                             │
│  优点：能发现人没想到的模式                                │
│  覆盖：长尾、组合异常                                      │
│  做法：把本期账务摘要（脱敏聚合数据，非明细）交给模型，      │
│        要求输出异常项 + 理由 + 建议动作                     │
│  限制：只在规则通道无发现时才值得跑；结果一律 WARNING 级     │
└──────────────────────────────────────────────────────────┘
```

**为什么不直接全用 AI**：风险预警误报的代价很高——用户会逐渐忽略所有提示（狼来了效应）。
确定性规则先把手上的高频风险管住，AI 只做补充，且结果永远标注"AI 推测"。

### 5.2 风险规则清单（内置）

#### A. 税务风险（TAX）

| code | 级别 | 定义 | 逻辑 |
|---|---|---|---|
| `TAX_BURDEN_ANOMALY` | WARNING | 增值税税负率异常 | `本期应交增值税 / 本期收入` 与近 6 个月均值偏离 > 50%，或 < 行业下限 |
| `TAX_INPUT_NO_OUTPUT` | WARNING | 有进项无销项 | 连续 3 个月 `销项税额 == 0 且 进项税额 > 0` |
| `TAX_LONG_CREDIT` | WARNING | 长期留抵 | `期末留抵 > 近 3 个月平均销售额`，或留抵持续 > 6 个月 |
| `TAX_UNCERTIFIED_AGING` | WARNING | 未认证进项账龄过长 | `22210102` 余额 > 0 且最早挂账 > 180 天 |
| `TAX_VAT_BALANCE_MISMATCH` | **CRITICAL** | 未交增值税与申报表不符 | `222102` 余额 ≠ 申报表第32行（勾稽 G4） |
| `TAX_DEDUCT_INELIGIBLE` | WARNING | 疑似不得抵扣项目已抵扣 | 品名含餐饮/娱乐/福利且 `isDeductible=true` |
| `TAX_MISSING_INVOICE` | INFO | 无合规票据支出 | 凭证 §"无票" 标记金额合计 > 阈值 |
| `TAX_RATE_MISMATCH` | WARNING | 税率与业务不匹配 | 如"餐饮服务"开 13%，"咨询服务"开 13% |

#### B. 账务风险（ACCOUNTING）

| code | 级别 | 定义 |
|---|---|---|
| `ACC_BALANCE_INVARIANT` | **CRITICAL** | 不变式 I2/I3/I4 不通过（见 03 章） |
| `ACC_CASH_NEGATIVE` | WARNING | 库存现金或银行存款出现贷方余额（透支/漏记） |
| `ACC_GROSS_MARGIN_NEGATIVE` | WARNING | 毛利率为负（`营业收入 < 营业成本`） |
| `ACC_EXPENSE_SPIKE` | INFO | 某费用科目环比增长 > 200% 且金额 > 阈值 |
| `ACC_AR_AGING` | WARNING | 应收账款账龄 > 1 年金额占比 > 30% |
| `ACC_AP_LONG_UNPAID` | INFO | 应付账款挂账 > 1 年未付 |
| `ACC_DUPLICATE_SUMMARY` | WARNING | 同期间同金额同摘要的凭证 ≥ 3 张（疑似重复入账） |
| `ACC_ROUND_NUMBER` | INFO | 大量整数金额（如 10000.00）凭证，疑似暂估或凑数 |

#### C. 舞弊/异常（FRAUD）

| code | 级别 | 定义 |
|---|---|---|
| `FRD_SAME_AMOUNT_BURST` | WARNING | 同一供应商 30 天内 ≥ 5 张金额相近（±1%）发票 |
| `FRD_NEAR_THRESHOLD` | INFO | 大量顶额票（如 9999.xx、49999.xx），疑似拆分 |
| `FRD_WEEKEND_INVOICE` | INFO | 开票日期集中在非工作日且数量异常 |
| `FRD_NEW_SUPPLIER_LARGE` | WARNING | 新供应商首笔即大额（> 阈值） |
| `FRD_PARTNER_BANK_CHANGED` | WARNING | 收款账户与历史不一致（改单诈骗） |
| `FRD_SELF_DEALING` | WARNING | 供应商与客户为同一主体（对开票） |

#### D. 合规风险（COMPLIANCE）

| code | 级别 | 定义 |
|---|---|---|
| `CMP_CONTRACT_OVER_INVOICE` | WARNING | 累计开票额 > 合同额 × 110% |
| `CMP_CONTRACT_EXPIRED_ACTIVE` | INFO | 合同已到期但仍产生新发票/收付款 |
| `CMP_INVOICE_DIRECTION` | **CRITICAL** | 进项票购买方非本主体（识别或录入方向错误） |
| `CMP_PERIOD_DATE_MISMATCH` | WARNING | 凭证日期与所属期间不符 |
| `CMP_MISSING_ATTACHMENT` | INFO | 凭证标记有附件但未关联任何单据 |

#### E. AI 质量（AI）

| code | 级别 | 定义 |
|---|---|---|
| `AI_LOW_AUTO_RATE` | INFO | 自动入账率 < 50%（提示优化规则或提示词） |
| `AI_HIGH_CORRECTION_FIELD` | INFO | 某字段纠错率 > 15%（提示改提示词） |
| `AI_COST_SPIKE` | WARNING | 单日 AI 成本 > 预算阈值 |
| `AI_PROVIDER_DOWN` | **CRITICAL** | Provider 连续失败 ≥ 5 次（熔断提示） |

### 5.3 规则的定义方式（无需改代码）

```jsonc
{
  "code": "TAX_VAT_BALANCE_MISMATCH",
  "category": "TAX",
  "level": "CRITICAL",
  "engine": "SQL",
  "definition": {
    "sql": "SELECT ... FROM account_balance ab JOIN ... WHERE ...",
    "params": { "tolerance": 0.01 },
    "messageTemplate": "账上未交增值税余额 {ledger}，申报表期末未缴 {filing}，差异 {diff} 元",
    "suggestionTemplate": "请检查 S3 转出未交增值税凭证是否生成、或申报表是否填错"
  }
}
```

- `messageTemplate` 必须能渲染出**带具体数字**的说明，而不是"存在风险"。
- `suggestionTemplate` 必须给出**下一步动作**。
- 每条规则有 `level`，`CRITICAL` 会阻塞月结（检查项 11）。

### 5.4 告警呈现

```
风险看板
├─ CRITICAL  (锁定月结)  ██ 2 条
│   ├─ 未交增值税与申报表不符   差异 5,200.00 元   [查看明细] [标记已处理]
│   └─ 账务不变式 I2 不通过                      [一键重算余额]
├─ WARNING   ██████ 8 条
├─ INFO      ███ 15 条（可折叠）
└─ 已处理 / 已忽略（保留记录）
```

每个告警：**标题 + 具体数字 + 证据（可点开看原始凭证/发票）+ 建议动作 + 处理状态**。
「已忽略」必须填理由，并进入 `AuditLog`。

### 5.5 AI 异常检测的提示词（补充通道）

```
输入（脱敏聚合，不发明细）:
{
  "period": "2025-03",
  "revenue": 285000.00, "cost": 210000.00, "grossMargin": 0.263,
  "expenseByCategory": { "办公费": 3200, "差旅费": 8600, "咨询服务费": 45000, ... },
  "topSuppliers": [{ "name": "某某咨询（脱敏）", "amount": 45000, "count": 3 }],
  "changeVsLast3Months": { "咨询服务费": +320 },
  "vat": { "outputTax": 37050, "inputTax": 12800, "payable": 24250 }
}

任务: 找出可能存在的记账错误、税务风险或异常模式。
要求: 只报告有具体数据支撑的异常，每条给出行项目、数字、你的判断理由、
      以及建议的核查动作。不确定的不要报。最多 5 条。
输出: JSON
```

**注意脱敏**：默认只发聚合数字与脱敏后的名称，不发原始发票图片、银行账号、身份证号。
`TaxProfile` 级别的开关控制是否允许发送明细。

### 5.6 报销合规自检（与风险预警的关系）

报销自检是风险预警体系的一个**具体应用场景**，但它的定位比一般风险提示更严格：
必须明确声明**不是税务意见、不是审计结论**。

**两类结论的界线**（这条界线必须写进代码，不能靠文案约束）：

| 类别 | 判据 | 措辞约束 |
|---|---|---|
| 数据矛盾 | 数据本身就能证明有问题（同一张票被两张凭证引用） | 可以说"必然有一处是错的" |
| 形态可疑 | 形态可疑但可能是正常业务（连号发票） | **禁止**出现"违规""违法"字样 |
| 仅作提示 | 供参考（缺附件、周末招待） | 中性描述 |

**为什么形态可疑类不能措辞为"违规"**：
同一供应商一天开 5 张连号票，可能是正常多次采购，也可能是拆分；
系统没有能力区分，把它说成"违规"就是**把判断责任推给了软件**，
而用户会当成结论。所以只报形态，判断权留给人。

**每条结论必须四段齐全**：哪里不对 · 该怎么核实 · 规则依据 · 涉及的具体凭证。
只说"有问题"而不说"怎么查"等于没说 —— 用户拿到一条无法行动的告警，只会关掉它。

**规则实现原则：宁可漏报，不可误报**。
一条误报会让人对整个自检失去信任，之后真问题也不会看。
所以每条规则都要有一个"必须命中"的用例和一个"必须不命中"的反例。

### 5.7 税务政策检索（不是 AI 功能，但必须说清边界）

政策检索按用户要求做成"每月自动检索报税地政策"，
但它**刻意不做** AI 解读与适用性判断。理由与 5.6 相同：
政策的适用取决于正文里的限定条件，只有人能判断。

| 做 | 不做 |
|---|---|
| 抓官方来源的**原文** | 抓第三方解读站点 |
| 存文号、发文日期、施行/失效日期、来源链接 | 判断"这条政策适用于你" |
| 存**抓取时间**与内容哈希 | 用摘要替代原文 |
| 把「同时符合下列条件」单独摘出来 | 给出"最优申报方式"建议 |

**为什么必须存抓取时间**：政策会改，同一链接在不同时间看到的内容可能不同。
没有抓取时间，事后无法判断"当时看到的是哪一版"。

**为什么用内容哈希**：政策被修订时链接与标题往往都不变，只有正文变了。
这类变更最容易漏，必须靠哈希比对单独报出来。

**为什么抓取器可注入**：① 内网/离线环境也要能用；
② 抓取失败必须能被看见 —— 全部来源失败时必须明确声明
"这不代表没有新政策"，而不是静默返回空。
## 6. 成本控制

| 手段 | 说明 |
|---|---|
| PDF 文本层优先 | 电子发票（占多数）不走视觉模型，成本降一个数量级 |
| `requestHash` 缓存 | 同一文件重复识别直接命中 `AiCallLog`，不再调 API |
| 图片压缩 | 长边 2000px、JPEG q80，足够识别，token 数显著下降 |
| 前缀缓存 | 长系统提示词放前缀，支持缓存的服务商可省 50%+ |
| 批量处理 | 夜间批量跑，避开高峰期限流 |
| 预算熔断 | 日/月成本上限，超限自动转人工（`AI_DAILY_BUDGET`） |

**成本量级估算**（一张发票一次视觉调用，压缩后约 1000~1500 input tokens）：

| 场景 | 单票成本量级 | 100 张/月 |
|---|---|---|
| 云端多模态模型 | 几分钱 | 几元 |
| 电子发票走文本层 | 更低 | 更低 |
| Mock / 本地模型 | 0 | 0 |

> 对小组织来说，成本不是主要矛盾——**准确率和"记不记错"才是**。
> 所以默认策略是"宁可多花几分钱调好模型，也不要为了省成本用弱模型导致人工返工"。
