# 06 · 税务与报表（一般纳税人）

> 目标：**账做完，申报表就出来了**。所有数字都能追溯到具体凭证，不允许出现"报表上有个数，但说不清哪来的"。

## 1. 一般纳税人增值税：科目 ↔ 申报表 映射总图

### ★ 核心勾稽（结账与申报前必跑）

| # | 勾稽关系 | 用途 |
|---|---|---|
| G1 | `Σ22210105本期贷方发生额` == 附列资料一「按适用税率」税额合计 | 销项不多不少 |
| G2 | `Σ22210110本期贷方发生额` == 附列资料一「简易计税」税额合计 | |
| G3 | `Σ22210101本期借方发生额（不含结转）` == 附列资料二第35行税额 | 进项与认证一致 |
| G4 | `主表第32行期末未缴` == `22210107 未交增值税期末余额` | **最重要的一条** |
| G5 | `22210106进项税额转出发生额` == 附列资料二第13行 | |
| G6 | `TaxFiling.payload` 与当期 `VatPeriodAggregate` 完全一致 | 报表与底稿不脱节 |

> G4 是税务稽查最爱查的点：账上挂着未交增值税，申报表上却是 0（或反之），
> 说明有账外经营或漏申报。这条自动校验能救命。

## 3. 附加税费

**计税依据** = 实际缴纳的**增值税 + 消费税**（本系统无消费税 → 即增值税）

| 税费 | 税率 | 科目 |
|---|---|---|
| 城市维护建设税 | 市区 7% / 县镇 5% / 其他 1% | `222105` |
| 教育费附加 | 3% | `222106` |
| 地方教育附加 | 2% | `222107` |

**六税两费减半**（财政部 税务总局公告 2023 年第 12 号等）：
增值税小规模纳税人、小型微利企业和个体工商户，减半征收资源税、城市维护建设税、
房产税、城镇土地使用税、印花税（不含证券交易印花税）、耕地占用税和教育费附加、地方教育附加。

```
应纳附加税费 = 应交增值税 × (城建税率 + 3% + 2%) × 减免比例
             = 应交增值税 × 12% × 50%
```

系统在 `TaxProfile` 里配置 `surtaxRates` 与 `surtaxReduction`，月结 S4 自动计提。

### 4.2 小型微利企业优惠（系统内置）

**判定条件**（同时满足）：
- 年度应纳税所得额 ≤ 300 万元
- 从业人数 ≤ 300 人
- 资产总额 ≤ 5000 万元

**优惠计算**（现行政策，2027 年 12 月 31 日前）：
应纳税所得额**减按 25% 计入**，按 **20% 税率**缴纳 → 实际税负 **5%**

```
减免所得税额 = 应纳税所得额 × (25% − 5%) = 应纳税所得额 × 20%
```

系统在 `TaxProfile.isSmallLowProfit = true` 时自动套用，并在申报表底稿上标注政策依据。

> ⚠️ 政策会变。系统的做法：**税率与优惠参数全部配置化**（`TaxProfile` + `system_config`），
> 并在 UI 上显示"当前适用政策与生效期间"，便于用户核对。不把税率硬编码进业务逻辑。

### 4.3 月度计提 vs 季度申报

小企业实务：**按月计提所得税费用，按季申报缴纳**。

```
每月（月结 S6）：计提所得税费用
  借 6801 所得税费用            （按当月利润总额估算）
    贷 222103 应交企业所得税
季度末：按实际申报数调整差额（多提冲回 / 少提补提）
  借/贷 6801 所得税费用
    贷/借 222103 应交企业所得税
缴纳时：
  借 222103 应交企业所得税
    贷 1002 银行存款
```

### 5.3 现金流量表

**主表（直接法）** —— 由 `Account.cashflowTag` 驱动的自动归集：

```
┌─ 一、经营活动产生的现金流量 ──────────────────────────┐
│ 销售产成品、商品、提供劳务收到的现金                     │
│   ← 1002/1001 借方发生额，对方科目为 6001/1122/2203      │
│ 收到其他与经营活动有关的现金                            │
│ 购买原材料、商品、接受劳务支付的现金                     │
│ 支付的职工薪酬                                        │
│ 支付的税费  ← 对方科目为 2221xx 的现金支出              │
│ 支付其他与经营活动有关的现金                            │
│ 经营活动产生的现金流量净额                              │
├─ 二、投资活动产生的现金流量 ──────────────────────────┤
│ 收回短期投资、长期债券投资和长期股权投资收到的现金        │
│ 取得投资收益收到的现金                                 │
│ 处置固定资产、无形资产和其他长期资产收回的现金净额        │
│ 购建固定资产、无形资产和其他长期资产支付的现金            │
│ 投资活动产生的现金流量净额                              │
├─ 三、筹资活动产生的现金流量 ──────────────────────────┤
│ 取得借款收到的现金                                     │
│ 吸收投资者投资收到的现金                                │
│ 偿还借款本金支付的现金                                  │
│ 偿还借款利息支付的现金                                  │
│ 分配利润支付的现金                                     │
│ 筹资活动产生的现金流量净额                              │
├─ 四、现金净增加额 ────────────────────────────────────┤
│ 加：期初现金余额                                       │
│ 五、期末现金余额                                        │
└───────────────────────────────────────────────────────┘
```

**取数算法**：对每一笔涉及 `1001/1002` 的凭证，取其**对方科目**，按 `Account.cashflowTag` 归类。

```
for each voucher where 涉及现金科目:
  现金行 = 1001/1002 的行
  对方行 = 同一凭证的其他行
  for each 对方行:
    tag = account(对方行).cashflowTag
    如果 tag 为空 → 用对方科目的 category 推断（ASSET→投资, LIABILITY/EQUITY→筹资, PROFIT_LOSS→经营）
    归入 tag 对应项目，金额 = min(现金行金额, 对方行金额) 按比例分摊
```

**★ 校验**：`五、期末现金余额 == 资产负债表「货币资金」期末余额`，不一致则出表并高亮差异。

**附表（间接法）**：净利润 → 调整非付现项目 → 经营活动现金流。
第一版**只做验证性展示**（用于内部核对），不作为正式申报表输出，因为小企业年度申报通常只要求主表。

### 5.4 反向取数：从"别人出的报表"反推科目余额

前面 5.1 / 5.2 讲的是**正向出表**（有账 → 生成报表）。
但在历史建账场景里，方向是反的：**没有账，只有别人（代账公司 / 税局）出的报表**。
这时要从报表行项目反推科目余额，作为期初建账的取数依据。

方向一反，风险也跟着反：

| | 正向出表 | 反向取数 |
|---|---|---|
| 数据来源 | 我们自己算的，可信 | 别人的表，口径可能不同 |
| 主要风险 | 算错 | **映射错**（把合计行当明细、把"减：X"当合计行） |
| 出错后果 | 报表数字不对 | **资产被重复确认 / 科目凭空消失** |

因此反向取数有三条硬规则：

**规则 1：合计行一个都不映射。**
「流动资产合计」「资产总计」「负债合计」「所有者权益合计」——
这些行是明细行的**和**。映射到任何科目都等于把已经进账的明细再确认一遍。
按恒等式，资产总计 = 负债合计 + 所有者权益合计，重复确认会让整个期初表膨胀一倍。

**规则 2：「减：」「加：」是列示前缀，不是合计行。**
报表里的「减：累计折旧」指向的是**独立的科目 1602**；
「加：营业外收入」指向的是**6301**。
把带这些前缀的行当合计行丢掉，会让累计折旧凭空消失 ——
固定资产净值虚高整整一个折旧额。这是个会直接记错账的坑，已有专门测试守着。

**规则 3：无法唯一确定的科目不猜。**
「应交税费」在报表上只有一行，但它可能是未交增值税、应交企业所得税、
待抵扣进项税额中的任何一个 —— 这是**会计判断**而不是识别问题，且没有唯一答案。
按借方还是贷方判断只能缩小范围（贷方=欠税，借方=多交或待抵扣），仍不唯一。
所以这一项不映射，期初税额以**申报表**为准（那里本来就准，且是权威口径）。

**归一化的边界：剥前缀，不做模糊包含。**

```
「一、货币资金」        → 货币资金     ← 剥序号
「（一）货币资金」      → 货币资金     ← 剥序号
「货币资金合计」        → 货币资金     ← 剥"合计"后缀（先判是否合计行，再剥）
「减：累计折旧」        → 累计折旧     ← 剥列示前缀
「应收账款」            → 应收账款
「预收账款」            → 预收账款     ← ★ 绝不能被"应收账款"匹配到
```

用**等值匹配**而不是包含匹配：包含匹配会让「应收账款」命中「预收账款」，
而这两个科目的方向完全相反 —— 这是最典型也最致命的一类映射错误。

**取数优先级**：已建档报表 > 人工输入 > 倒轧

报表是别人出的表，人工输入是"我记得大概是这个数"，两者可信度不同。
这个优先级直接决定期初方案里那一行的 `source` 标注：

```
DECLARED  取自报表（有据）
MANUAL    人工提供
DERIVED   倒轧推算（★ 必须人工确认）
```

**只有期末余额参与取数。** 期初余额属于更早的期间，
而期初建账要的是"启用前一日的余额"，即最后一期报表的期末数。
同理，多期报表不混用：只取启用日之前**最近一期**，取不到才退而取最早一期并明确标注口径不符。

**界面必须回答"我传的表到底用上了没有"。**
`GET /api/history/declared-statements` 返回：映射成功的科目余额 +
被跳过的行及其原因（合计行 / 应交税费 / 不在别名表内 / 同科目金额冲突）。
用户看得到"哪些用上了、哪些没用上、为什么"，才敢相信这个期初表。

### 5.5 底稿生成：从科目余额到申报表

第 5.1~5.3 节讲的是「报表长什么样」，这一节讲「数从哪里来」。

**归集机制**：科目表的每个科目都带 `reportItem` 标记，
报表按标记归集而不是在代码里硬编码科目对应关系。同一标记下多个科目自动合并。

| 坑 | 后果 | 修法 |
|---|---|---|
| 备抵科目与主科目共用标记（`1602` 与 `1601`） | 直接相加，固定资产虚增一个折旧额，**报表看起来完全正常** | 拆开标记；`减：累计折旧` 单独成行，作为减项 |
| 损益类用余额取数 | 期末结转后余额为 0 → **一张全 0 的利润表** | 必须用本期发生额 |
| 定义引用了不存在的标记 | 该行静默恒为 0，**数字凭空消失** | 生成前做覆盖自检，缺失即报出来 |

**表内勾稽自检**：资产总计 = 负债和所有者权益总计、营业利润公式、
净利润公式等，逐条给出期望值与实际值。★ 不通过时**只报告，不调整** ——
不平衡通常意味着科目用错（该记预收的记成了应收），
在报表上"调平"会把真实错误藏起来。

**该判断的留空**：企业所得税的口径大量依赖专业判断。
自动算出的调整额如果错了，用户会直接照着申报 —— 那比不给结果更糟。
所以纳税调整项、年度税率、优惠适用一律留空并写明依据要求。

**附加税费**：计税依据是**本期实际应缴纳的增值税**，不是销项税额。
城建税税率按纳税人所在地分档（市区 7% / 县镇 5% / 其他 1%），需按报税地配置。

### 关于"可导入税务系统"

现实情况（重要，避免做无用功）：

1. **全国统一规范电子税务局**（新电子税局）目前**不提供通用的财务报表/申报表文件导入接口**
   给普通企业。企业要么在网页上手工填，要么用**已通过税局对接认证的商业财务软件**的直连接口。
2. 因此本系统的第一版策略是**底稿模式**：导出与税局网页**字段一一对应、行次完全一致**的 Excel，
   用户照着填（每个格子都能对上，5 分钟填完），或直接打印对照。
3. 系统**预留导出器接口** `TaxExportProvider`，将来若接入某省的导入格式或第三方对接通道，
   实现一个新的 Provider 即可，业务代码不动。

```
interface TaxExportProvider {
  readonly region: string;          // 'CN-GENERAL' | 'CN-SH' | ...
  readonly supports: TaxType[];
  /** 导出可直接导入税局的文件 */
  export(filing: TaxFiling): Promise<{ filename: string; buffer: Buffer }>;
}
```

> 我们**不假装**能一键直连报税。老老实实把底稿做到"抄起来零思考"，比做一个跑不通的导入按钮有用得多。

## 7. 税务相关的风险预警（详见 07 章）

| 预警 | 触发 |
|---|---|
| 税负率异常 | 本期增值税税负率 与 行业/历史 偏离 > 阈值 |
| 进销项不匹配 | 有进项无销项（或反之）连续 3 个月 |
| 长期留抵 | 期末留抵 > 3 个月销售额 |
| 未认证进项超期 | 待认证进项税额账龄 > 360 天 |
| 未交增值税异常 | `222102` 余额与申报表第32行不一致 |
| 收入成本倒挂 | 毛利率为负 |
| 票据异常 | 同一供应商短期内大量顶额开票（9999.99 类） |

## 8. 时效性声明

> 税率、优惠政策、申报表行次会随政策调整。
> 本文档记录的是**设计时刻**的口径，所有可变参数（税率表、优惠比例、起征点、申报表行次）
> 都**存放在数据库配置中**（`TaxProfile` + `system_config` + `VatRateCode`），
> 而不是硬编码在业务逻辑里。政策变化时改配置即可，并在 UI 上标注政策文号与生效期间。
