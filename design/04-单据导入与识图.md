# 04 · 单据导入与识图

> 目标：把"一堆图片和 PDF"变成"结构正确、可入账的票据对象"，并且**在人看之前就把明显错误拦下来**。

## 1. 导入通道

| 通道 | 场景 | 实现 |
|---|---|---|
| 拖拽上传 | 最常用，一次 10~100 个文件 | 前端 `el-upload` 分片上传 → `POST /documents/batch` |
| 选择文件夹 | 从下载目录批量导入 | `<input webkitdirectory>`，前端遍历后逐个上传 |
| 邮箱收单 | 电子发票自动进邮箱 | IMAP 轮询（作业），附件落库。**第一版可选** |
| 银行流水 Excel | 导出对账单 | `POST /documents/bank-statement` + 列映射向导 |
| 手工录入 | AI 失败或小额现金 | 直接开表单，**不生成 Document**，只生成 Invoice |

上传即落库，**不等识别结果**。响应返回 `documentId` 列表，识别在后台作业里跑。
前端用轮询（2s）或 SSE 订阅状态。

## 2. 去重：两道关卡

### 关卡一：文件内容哈希（防止同一文件重复上传）

```
contentHash = sha256(fileBytes)
UNIQUE(entityId, contentHash)   -- 数据库唯一索引
```

命中 → 直接返回已存在的 `documentId`，不产生新记录。

### 关卡二：业务唯一键（防止不同文件描述同一张票）

同一张发票可能被：扫描件 + 电子原件 + 微信转发压缩版，三种文件、三个哈希，一张票。
所以识别成功后必须再查一次业务唯一键：

```sql
-- 数电票
SELECT * FROM invoice WHERE entity_id=$1 AND direction=$2
  AND invoice_number=$3 AND is_red_flushed=$4;
-- 纸质/老电票
SELECT * FROM invoice WHERE entity_id=$1 AND direction=$2
  AND invoice_code=$3 AND invoice_number=$4 AND is_red_flushed=$5;
```

命中 → 把新 `documentId` 挂到已有发票的 `DocumentLink`（作为补充附件），
**不创建新发票**，前端提示"该发票已存在，已作为附件补充"。

> 这是"别记错"的第一道实质防线。重复入账是自动记账最常见、也最致命的错误。

## 3. 识图架构：Provider 适配层

```
                          ┌────────────────────────────┐
   Document ──▶ 预处理 ───▶│  OcrProvider (interface)   │
                │          │  ├ MockOcrProvider   (dev)  │
                │          │  ├ OpenAiCompatProvider ★  │
                │          │  │   (baseUrl 可指向        │
                │          │  │    DeepSeek/Qwen-VL/     │
                │          │  │    豆包/GLM-4V/自建)      │
                │          │  └ LocalOcrProvider  (可选)  │
                │          └───────────┬────────────────┘
                │                      │ 返回严格 JSON
      ┌─────────▼─────────┐            ▼
      │ 预处理             │   ┌──────────────────────┐
      │ · PDF 文本层优先    │   │ Schema 校验           │
      │ · 图片压缩/纠偏     │   │ + 会计规则交叉校验     │
      │ · 可选区域脱敏      │   └──────────┬───────────┘
      └───────────────────┘              │
                                ┌────────▼─────────┐
                                │ 置信度评分 → 路由  │
                                └────────┬─────────┘
                         高置信度 ────────┴──────── 低置信度
                    AUTO_DRAFTED               NEEDS_REVIEW
```

### Provider 接口

```ts
export interface OcrProvider {
  readonly name: string;
  /** 健康检查：配置是否正确、服务是否可达 */
  ping(): Promise<{ ok: boolean; model?: string; message?: string }>;
  /** 结构化抽取：输入文件 → 输出符合 schema 的对象 */
  extract<T>(req: ExtractRequest): Promise<ExtractResponse<T>>;
  /** 成本预估（用于用量看板与"贵不贵"决策） */
  estimateCost(req: ExtractRequest): Promise<Decimal | null>;
}

export interface ExtractRequest {
  filePath: string;           // 本地临时路径或对象存储临时 URL
  mimeType: string;
  targetType: 'INVOICE' | 'BANK_SLIP' | 'CONTRACT' | 'BANK_STATEMENT';
  schema: JsonSchema;         // packages/shared 中定义，见第 5 节
  promptKey: string;          // packages/prompts 中模板标识
  promptVersion: string;
  textLayer?: string;         // PDF 已提取的文本层（有则优先用，省 token 且更准）
  hints?: Record<string, unknown>;  // 如 { entityName, entityTaxNo } 用于方向判断
  timeoutMs?: number;
}

export interface ExtractResponse<T> {
  data: T;
  /** 字段级置信度：{ fieldName: 0..1 } */
  fieldConfidence: Record<string, number>;
  overallConfidence: number;
  rawText?: string;
  raw?: unknown;              // 模型原始响应，存 AiCallLog
  provider: string;
  model: string;
  latencyMs: number;
}
```

### 为什么 `baseUrl` + `model` 就够了

DeepSeek、通义千问 VL、豆包、智谱 GLM-4V、以及 vLLM/Ollama 自建的模型，
**绝大多数都暴露 OpenAI 兼容的 `/v1/chat/completions`**。所以：

```bash
# 换成通义千问 VL
AI_PROVIDER=openai-compatible
AI_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
AI_VISION_MODEL=qwen-vl-max

# 换成自建本地模型（数据不出内网）
AI_PROVIDER=openai-compatible
AI_BASE_URL=http://host.docker.internal:11434/v1
AI_VISION_MODEL=qwen2.5-vl:7b

# 开发环境：不花钱
AI_PROVIDER=mock
```

一个适配器覆盖 90% 场景。未来遇到不走 OpenAI 协议的（如某些票据专用 OCR API），再单独加 Provider 实现。

## 4. 处理流水线（详细）

```
① 入库          Document(status=PENDING)
                 └ 计算 contentHash，唯一索引去重
② 预处理
   ├ PDF：先尝试取文本层（pdf-parse）
   │    └ 文本层质量够（字符数 > 阈值且含"发票"字样）→ 走文本模式
   ├ 图片：sharp 转 JPEG、限长边 2000px、EXIF 旋转纠正
   └ 可选脱敏：裁掉银行账号/身份证区域（隐私模式）
③ 定向           按 docType 选 schema 与 prompt
                  └ 若用户声明类型与识别结果不符 → 置 detectedType 并产生风险提示
④ 抽取           OcrProvider.extract()
                  └ 失败 → 重试 maxRetries，仍失败 → status=FAILED
⑤ Schema 校验    Zod 严格校验字段类型、必填、枚举
                  └ 金额字段强制 Decimal，字符串去空格/全角转半角
⑥ 会计交叉校验   见第 5 节 —— ★ 这一步比模型本身更重要
⑦ 置信度评分     模型分 × 0.6 + 校验通过率 × 0.4，并按字段加权
⑧ 路由
   ├ conf ≥ 0.85 且无冲突 → 建 Invoice(status=AUTO_DRAFTED) → 触发自动记账
   └ 否则               → 建 Invoice(status=NEEDS_REVIEW) → 进人工队列，高亮低置信字段
⑨ 落痕           AiCallLog + ExtractionResult（含字段级置信度与 bbox）
⑩ 归档           Document(status=EXTRACTED/REVIEW_REQUIRED)
```

## 5. 会计交叉校验规则（拦错的关键）

模型会看错，但**会计恒等式不会骗人**。每条规则给出 `PASS / WARN / FAIL`：

| # | 规则 | 级别 | 说明 |
|---|---|---|---|
| V1 | `金额 + 税额 == 价税合计`（允许 ±0.02 分差） | FAIL | 最强校验，能拦住大量 OCR 数字错误 |
| V2 | `税额 == round(金额 × 税率, 2)`（允许 ±0.02） | WARN | 税率识别错时触发 |
| V3 | 税率 ∈ {0, 0.005, 0.01, 0.015, 0.03, 0.05, 0.06, 0.09, 0.13} | FAIL | 非枚举值直接拒 |
| V4 | 购买方名称/税号 == 本主体 | **FAIL** | 拦"购销方颠倒"（进项票被当成销项） |
| V5 | 发票号码格式：数电票 20 位数字；老电票 code 12 位 + no 8 位 | WARN | 格式异常提示人工核 |
| V6 | 开票日期 ≤ 今天 且 ≥ 主体启用日期 | WARN | 未来日期/超远期票据 |
| V7 | 业务唯一键未重复（第 2 节关卡二） | **FAIL** | 命中则转"已存在"流程 |
| V8 | 金额 > 0 且 ≤ 配置上限（默认 1000 万） | FAIL | 天文数字多为识别错误 |
| V9 | 明细行金额合计 == 票面金额 | WARN | 数电票有明细行时 |
| V10 | 若为红字发票，必须能关联到原蓝票（或明确无原票） | WARN | 红冲处理依赖 |
| V11 | 进项票的税率合理性（如"餐饮服务"不应出现 13%） | INFO | 经验规则，AI 辅助 |
| V12 | 卖方税号在本主体 `Partner` 中已存在 | INFO | 新供应商 → 提示建档案 |

**V4 特别重要**：模型把购买方/销售方搞反，会导致进项票被记成销项，虚增收入和销项税——
这是最严重的一类错误。除了查名称，还要查税号，两者都查。

**校验结果如何影响路由**

```
存在任一条 FAIL                 → NEEDS_REVIEW（强制人工，且不允许"一键确认"绕过）
仅 WARN                        → 降置信度 0.15/条，可能落到 NEEDS_REVIEW
全部 PASS 且 conf ≥ 0.85       → AUTO_DRAFTED
```

## 6. 各类型票据的字段与提示词要点

### 6.1 增值税发票（专票/普票/数电票）

必抽字段：
```
invoiceCode, invoiceNumber, digitalInvoiceNo, invoiceDate,
sellerName, sellerTaxNo, buyerName, buyerTaxNo,
amountExclTax, taxRate, taxAmount, amountInclTax,
isRedFlushed, itemLines[{itemName, spec, quantity, unitPrice, amountExclTax, taxRate, taxAmount}]
```

提示词要点（固化在 `packages/prompts/invoice-extract@v1.md`）：

- 明确"**必须只输出 JSON，不要 Markdown 代码块，不要解释**"。
- 明确角色与用途：*"这是中国增值税发票，购买方是本企业。请严格按票面文字识别，不要推断、不要补全。"*
- **金额规则**：*"¥1,234.56 应输出 1234.56；'壹仟贰佰叁拾肆元伍角陆分' 大写金额是校验依据，如与小写不一致，取大写并在 `_warnings` 中说明。"*
- **方向规则**：*"若购买方名称为 '{entityName}'，则 direction='INPUT'；若销售方为 '{entityName}'，则 direction='OUTPUT'；两者都不是请返回 error。"*
- 输出附带 `_fieldConfidence` 与 `_warnings` 字段。

> 💡 **一个提升准确率的实用技巧**：把本主体的**名称和税号写进提示词**（`hints`），
> 让模型直接判断进/销方向，而不是事后用字符串匹配。实测能显著降低方向错误。

### 6.2 银行回单 / 流水

回单（单笔）必抽：`txnDate, direction, amount, counterpartyName, counterpartyAccountNo, summary, bankSerialNo`

流水（Excel 优先，不走识图）：
- 用 `exceljs` 读取，前端提供**列映射向导**（把"交易日期/借方金额/贷方金额/余额/摘要"映射到系统字段）。
- 若银行只给 PDF 流水 → 走识图，但需分页合并，且必须校验 `余额连续性`：
  `上笔余额 ± 本笔金额 == 本笔余额`，不连续则整批 `NEEDS_REVIEW`。
- 金额正负号：**统一按"收入为正、支出为负"还是"借贷两列"** 由映射向导决定，落库统一成 `direction + 正数金额`。

### 6.3 合同（备查）

只抽：`contractNo, name, counterpartyName, amountInclTax, taxRate, signDate, startDate, endDate, direction`

合同**不生成分录**。识别的价值在于：
1. 建立 `DocumentLink` 关联到后续发票；
2. 触发风险规则（合同额 vs 累计开票额、合同已到期仍开票）。

## 7. 人工复核界面（最重要的用户界面）

一张待复核票据的界面布局：

```
┌───────────────────────┬──────────────────────────────────────────┐
│                       │  ① 原始图片（左侧，可缩放/翻页）           │
│                       │     低置信字段在图上高亮 bbox              │
│   [发票原图]            │                                          │
│                       ├──────────────────────────────────────────┤
│                       │  ② 抽取字段表单（低置信字段黄色底纹）       │
│                       │     发票号码 [12345678] ⚠ 置信度 0.61      │
│                       │     价税合计 [1,130.00] ✓                 │
│                       ├──────────────────────────────────────────┤
│                       │  ③ 校验结果                                │
│                       │     ✓ V1 金额+税额=价税合计                │
│                       │     ✗ V4 购买方税号与本主体不一致！        │
│                       │       → 建议：这可能是一张销项发票          │
│                       ├──────────────────────────────────────────┤
│                       │  ④ 建议分录预览（来自规则引擎）            │
│                       │     借 管理费用—办公费   1,000.00          │
│                       │     借 应交税费—待认证进项税额 130.00      │
│                       │     贷 应付账款         1,130.00          │
│                       │     命中规则：采购-办公用品(v3) 置信度 0.92 │
│                       ├──────────────────────────────────────────┤
│                       │  ⑤ 操作：[确认入账] [修改后入账] [忽略]     │
└───────────────────────┴──────────────────────────────────────────┘
```

设计要点：

1. **原图与表单并排**，且低置信字段要在原图上框出来。人工核对速度提升数倍。
2. **校验失败必须解释原因**，并给"可能是什么"的建议，而不是只说"不对"。
3. **规则命中理由可见**（`命中规则：采购-办公用品(v3)`），让用户建立对系统的信任。
4. **一键确认只在高置信 + 全 PASS 时可用**。其余场景强制"修改后入账"，逼人看一眼。
5. 支持键盘流：`Tab` 跳字段、`Enter` 确认并跳下一张、`Esc` 忽略。批量场景效率关键。

## 8. 质量度量（AI 运维看板）

| 指标 | 计算 | 目标 |
|---|---|---|
| 自动入账率 | `AUTO_DRAFTED` / 总票据 | > 70% |
| 字段纠错率 | 人工修改过的字段数 / 总字段数 | < 5%，并按字段细分 |
| 校验拦截率 | 触发 FAIL 的票据数 / 总票据 | 观察值，> 2% 说明模型或版式有问题 |
| 单票成本 | `SUM(cost_estimate)` / 票据数 | 按 Provider 对比 |
| 平均延迟 | `AVG(latency_ms)` | < 15s |
| 重抽率 | 同一 document 多次抽取的比例 | 说明首次失败率高 |

`ExtractionResult.corrections` 记录人工改了什么，这是**优化提示词和训练规则的唯一可靠数据源**。
每两周看一次纠错 TOP 字段，针对性改提示词。

## 9. 失败与降级

| 情况 | 处理 |
|---|---|
| AI Provider 不可用 | 作业重试（指数退避 3 次）→ 仍失败则单据 `FAILED`，进人工录入队列，**不阻塞**其他单据 |
| 单票超时 | `AI_TIMEOUT_MS`（默认 60s）→ 计入重试 |
| 返回非法 JSON | 尝试修复（去 Markdown 包裹、截取首个 `{...}`）→ 失败则重试（提示词追加"上次输出不是合法 JSON"） |
| 返回 schema 不匹配 | 计入 FAIL，`NEEDS_REVIEW` 并展示原始响应供人工判断 |
| 额度耗尽 | Provider 返回 402/429 → 全局熔断，所有待处理单据转人工，UI 顶部横幅告警 |
| PDF 是加密的 | 提示用户提供密码或转图片 |

**核心原则：AI 挂了，账还得能记。** 手工录入通道永远可用，且与自动通道产出**完全相同的数据结构**。
