# 05 · 自动记账规则引擎 ★ 核心

> 系统的价值全在这一章：把「票据」变成「凭证」，并且**错了能被发现、改一次就学会**。

## 1. 三层决策架构

```
                    ┌─────────────────────────────────────┐
   票据 + 上下文 ───▶│ L1  确定性规则引擎                    │  优先级最高
                    │     条件树匹配 → 分录模板             │  可解释、可复现
                    │     命中率目标 > 75%                  │
                    └──────────────┬──────────────────────┘
                                   │ 未命中
                    ┌──────────────▼──────────────────────┐
                    │ L2  历史学习（用户纠错沉淀）           │
                    │     供应商/关键词/金额桶 → 科目        │  越用越准
                    │     ClassificationOverride            │
                    └──────────────┬──────────────────────┘
                                   │ 未命中
                    ┌──────────────▼──────────────────────┐
                    │ L3  AI 建议                          │  永远只是「建议」
                    │     相似历史凭证 few-shot → 科目建议   │  必带理由与置信度
                    │     conf < 阈值 → 强制人工            │
                    └──────────────┬──────────────────────┘
                                   │ 全部未命中
                                   ▼
                        进人工队列（并提示"是否创建规则"）
```

**为什么是这个顺序**：规则引擎出账**确定**（同一输入永远同一结果），
历史学习基于**你自己的**习惯，AI 兜底处理长尾。
任何时候 AI 挂掉、或用户不想花 API 钱，L1+L2 依然能把 80% 的账记对。

**输出的统一结构**（三层完全一致，上层不关心来源）：

```ts
export interface DraftVoucherSuggestion {
  lines: Array<{
    accountId: string;
    accountCode: string;
    accountName: string;
    direction: 'DEBIT' | 'CREDIT';
    amount: Decimal;
    summary: string;
    partnerId?: string;
  }>;
  source: 'RULE' | 'LEARNED' | 'AI' | 'MANUAL';
  ruleId?: string;
  ruleVersion?: number;
  confidence: Decimal;         // 0..1
  reason: string;              // ★ 人类可读的命中理由，写进凭证备注
  warnings: string[];          // 校验告警
  needsReview: boolean;
}
```

## 2. 规则结构

### 2.1 条件树（`JournalRule.conditions`）

用 JSON 表达，前端可视化编辑，不写代码：

```jsonc
{
  "op": "AND",
  "children": [
    { "field": "invoice.category",   "cmp": "IN",  "value": ["SPECIAL_VAT", "E_INVOICE"] },
    { "field": "invoice.direction",  "cmp": "EQ",  "value": "INPUT" },
    { "field": "invoice.isDeductible","cmp": "EQ", "value": true },
    { "op": "OR", "children": [
        { "field": "invoice.sellerName", "cmp": "CONTAINS", "value": "办公" },
        { "field": "invoiceLine.itemName", "cmp": "REGEX", "value": "(办公用品|文具|耗材)" }
    ]},
    { "field": "invoice.amountInclTax", "cmp": "BETWEEN", "value": [0, 50000] }
  ]
}
```

支持的比较符：

| cmp | 含义 | 适用类型 |
|---|---|---|
| `EQ` `NEQ` | 等于 / 不等于 | 任意 |
| `IN` `NOT_IN` | 属于集合 | 枚举/字符串 |
| `CONTAINS` `NOT_CONTAINS` | 包含子串 | 字符串（名称、摘要、品名） |
| `REGEX` | 正则匹配 | 字符串 |
| `GT` `GTE` `LT` `LTE` | 大小比较 | 金额、数量、日期 |
| `BETWEEN` | 闭区间 | 金额、日期 |
| `IS_NULL` `NOT_NULL` | 空判断 | 任意 |
| `STARTS_WITH` `ENDS_WITH` | 前后缀 | 字符串（发票代码、科目编码） |

**可引用字段（上下文对象）**

```
invoice.*        direction, category, sellerTaxNo, sellerName, buyerTaxNo,
                 amountExclTax, taxRate, taxAmount, amountInclTax, isRedFlushed,
                 hasItemLines, itemSummary
invoiceLine.*    itemName, spec, quantity, unitPrice, amountExclTax, taxRate
bank.*           direction, amount, counterpartyName, counterpartyAccountNo, summary
partner.*        taxNo, name, role, tags
contract.*       direction, amountInclTax, status, daysToExpiry
entity.*         taxpayerType, currentPeriod
learned.*        supplierAccountId, keywordAccountId   （来自 L2 的历史结论）
```

### 2.2 分录模板（`JournalRule.template`）

模板语法：`{{ 表达式 }}`，金额用 `Decimal` 运算。

```jsonc
{
  "summary": "采购{{ invoice.itemSummary || '物资' }}（{{ partner.name }}）",
  "attachments": 1,
  "lines": [
    { "side": "DEBIT",
      "account": "660202",                       // 科目编码（稳定标识，非 id）
      "amount": "{{ invoice.amountExclTax }}",
      "summary": "{{ invoice.itemSummary }}" },

    { "side": "DEBIT",
      "account": "{{ this.taxAccount }}",        // 由 taxTreatment 决定，见 2.3
      "amount": "{{ invoice.taxAmount }}",
      "summary": "进项税额",
      "when": "{{ invoice.taxAmount > 0 && invoice.isDeductible }}" },

    { "side": "CREDIT",
      "account": "{{ partner.defaultPayableAccount || '2202' }}",
      "amount": "{{ invoice.amountInclTax }}",
      "summary": "应付 {{ partner.name }}",
      "partnerId": "{{ partner.id }}" }
  ]
}
```

模板能力边界（**刻意做小**）：

| 能力 | 支持 | 说明 |
|---|---|---|
| 四则运算 + `round(x, 2)` | ✓ | 金额计算 |
| 条件行 `when` | ✓ | 该行金额为 0 或条件为假时整行省略 |
| 科目按编码引用 | ✓ | 编码比 id 稳定，便于规则导出/导入 |
| 变量插值到摘要 | ✓ | |
| 循环 / 子模板 / 函数定义 | ✗ | 需要就写代码级规则插件 |
| 跨凭证生成 | ✗ | 一张票只生成一张凭证（结转类除外，见 03 章 S 系列） |

> **不做图灵完备**是设计决策，不是偷懒。规则越强越难调试，而记账错误的代价很高。

### 2.3 `taxTreatment` 派生逻辑（进项税的关键）

模板里引用 `this.taxAccount`，由系统按下列决策算出，**规则作者不用操心**：

```
taxAccount 决策:
  if invoice.taxAmount == 0                      → 无税行
  elif invoice.isDeductible == false             → 无税行（税额并入成本金额）
  elif entity.taxpayerType == 'SMALL_SCALE'      → 无税行（小规模不可抵扣）
  elif taxProfile.invoiceCertMode == 'AUTO_ON_IMPORT' && 专票/数电票
                                                 → '22210102' 待认证进项税额
  elif 已在本期勾选认证                            → '22210101' 进项税额
  else                                           → '22210102' 待认证进项税额
```

`isDeductible == false` 时，**借方成本金额必须变成 `amountInclTax`**，而不是 `amountExclTax`。
这条容易写错，所以做成模板里的内建变量：

```jsonc
{ "side": "DEBIT",
  "account": "660202",
  "amount": "{{ invoice.isDeductible ? invoice.amountExclTax : invoice.amountInclTax }}" }
```

**必须 `isDeductible = false` 的典型场景**（系统内置识别）：

| 场景 | 依据 |
|---|---|
| 集体福利、个人消费 | 财税〔2016〕36号 附件1 第二十七条 |
| 业务招待费中的餐饮、娱乐 | 通常不得抵扣 |
| 旅客运输以外的普通发票 | 无抵扣凭证 |
| 简易计税项目、免税项目专用 | 用于不得抵扣项目 |
| 购进贷款服务 | 明确不得抵扣 |
| 未在规定期限内认证/勾选 | 逾期不得抵扣 |

系统在识别到 `itemName` 含「餐饮/娱乐/福利/礼品/贷款利息」时**自动建议** `isDeductible=false`，
但**必须人工确认**（因为存在例外，如餐费属于会议费可抵）。默认保守：不确定就不可抵扣，多交税总比被查好。

## 3. 场景 → 分录 全表

> 科目编码以 `design/09-数据字典-科目表.md` 为准。
> `★` 标记的是最容易被记错的地方，实现时必须有单元测试。

### A. 销项（OUTPUT）

| # | 场景 | 触发 | 分录 |
|---|---|---|---|
| A1 | 开票即确认收入 | 销项发票导入 | 借 `1122` 应收账款（价税合计）<br>贷 `6001` 主营业务收入（不含税）<br>贷 `22210105` 应交增值税(销项税额) |
| A2 | 开票但未收款且已预收 | 存在预收核销 | 借 `2203` 预收账款<br>贷 `6001` + 贷 `22210105` |
| A3 ★ | **已确认收入未开票** | 手工/进度确认 | 借 `1122`<br>贷 `6001`<br>贷 `22210109` **待转销项税额**（不是销项税额！） |
| A4 ★ | 后期补开发票 | 发票关联到 A3 | 借 `22210109` 待转销项税额<br>贷 `22210105` 销项税额（**只转税，不再确认收入**） |
| A5 | 销项红字发票 | `isRedFlushed=true` | 反向：借 `6001` + 借 `22210105`，贷 `1122` |
| A6 | 结转销售成本 | 手工或规则 | 借 `6401` 主营业务成本，贷 `1405` 库存商品 |
| A7 | 计提税金及附加 | 月结 S4 | 见 03 章 5.3 |
| A8 ★ | **应收账款坏账** | 小企业会计准则 | **直接转销法**：借 `6711` 营业外支出，贷 `1122`（**不设坏账准备**） |

> A3/A4 是最典型的错误点：很多人直接记销项税额，导致**提前交税**。
> 判据：增值税纳税义务发生时间 = 开票当天 OR 收款当天 OR 合同约定收款日，**三者孰早**。
> 未开票、未收款且无合同约定 → 用待转销项税额。

| # | 场景 | 分录 |
|---|---|---|
| B1 | 采购物资（专票，已认证） | 借 `1403` 原材料（不含税）+ 借 `22210101` 进项税额<br>贷 `2202` 应付账款（价税合计） |
| B2 ★ | 采购物资（专票，**未认证**） | 借 `1403` + 借 `22210102` **待认证进项税额**<br>贷 `2202` |
| B3 ★ | 认证后结转 | 借 `22210101` 进项税额，贷 `22210102` 待认证进项税额 |
| B4 | 费用票（管理/销售/财务） | 借 `6602xx`/`6601xx`/`6603` + 借 税科目<br>贷 `2202` 或 `1002` |
| B5 ★ | **不可抵扣**（福利/招待/个人消费） | 借 `6602xx` **（价税合计全额）**<br>贷 `2202`——**没有税行** |
| B6 ★ | **已抵扣后改变用途**（转出） | 借 `6602xx`/`1601`（成本）<br>贷 `22210106` 进项税额转出 |
| B7 ★ | 购进固定资产（设备） | 借 `1601` 固定资产 + 借 税科目，贷 `2202` |

| B9 ★ | **进项红字发票** | 反向：借 `2202`，贷 成本科目 + 贷 税科目 |
| B10 | 暂估入库（货到票未到） | 借 `1403` 原材料，贷 `2202` 应付账款—暂估；<br>次月冲回或收票后调整 |
| B11 ★ | 取得**不合规票据** | **不入账**（或入账但纳税调增）。系统标记 `NEEDS_REVIEW` + 风险提示 |
| B12 ★ | 旅客运输（火车/机票） | 借 `6602xx` 差旅费（不含税）+ 借 `22210101`<br>（**普票也可抵**，按 9%/3% 计算抵扣） |

## 4. L2 历史学习（越用越准）

用户每次纠正自动分录，系统记一笔 `ClassificationOverride`。

### 特征提取

```
featureKey 生成规则（按优先级取第一个可用）:
  1. supplier:{sellerTaxNo}                    // 同一供应商，最强信号
  2. supplier:{normalizedSellerName}           // 无税号时
  3. keyword:{topItemKeyword}|supplier:{taxNo} // 供应商 + 品名关键词
  4. keyword:{summaryKeyword}                  // 银行流水摘要关键词
```

`normalizedSellerName`：去括号内容、去"有限公司/股份/科技/商贸"等后缀、全角转半角、去空格。

### 命中与生效

```
L2 查询:
  SELECT * FROM classification_override
   WHERE entity_id=$1
     AND (feature_key = $taxNoKey OR feature_key = $nameKey OR feature_key = $keywordKey)
   ORDER BY hit_count DESC, last_used_at DESC LIMIT 1;

命中后:
  · 输出 source='LEARNED'，confidence = min(0.98, 0.7 + 0.05 * hit_count)
  · 只有 hit_count >= 2 且 confidence >= 0.8 才允许"一键确认"
  · 每次命中 hitCount++ → 用得越多越可信
```

### 从纠错到规则的晋升

```
同一 featureKey 被人工纠正 N 次（默认 N=3，可配置）:
  → 弹出提示："你已 3 次把『XX公司』的发票记到『管理费用—咨询费』，
     是否创建自动规则？"
  → 用户点确认 → 生成一条 JournalRule（priority 取当前最大值+10，即低优先级）
  → 规则可解释、可编辑、可停用
```

> 这个"晋升"机制是关键：让系统的行为从**黑盒统计**变成**用户看得懂的规则**。
> 用户随时能知道"为什么这么记"。

## 5. L3 AI 建议

只在 L1/L2 都未命中时调用。

```
Prompt 结构（packages/prompts/account-suggest@v1.md）:

  系统: 你是中国小企业会计准则的记账助手。根据票据信息和相似历史凭证，
        从给定科目表中选出最合适的科目。只输出 JSON。
  上下文:
    【本主体科目表】（只给末级、启用的，含编码与名称，~200 个，用编码:名称紧凑格式）
    【票据信息】{ structured fields }
    【相似历史凭证】（向量/关键词检索出的 5 条已过账凭证，含摘要与科目）
    【供应商历史】该供应商过去 10 次的科目分布
  输出 schema:
    { "suggestions": [
        { "lines": [{ "accountCode": "660202", "direction": "DEBIT", "amountExpr": "amountExclTax" }],
          "confidence": 0.0-1.0,
          "reason": "一句中文理由" } ],
      "warnings": ["..."] }
```

**硬约束（在代码里强制，不靠提示词）**：

1. AI 返回的 `accountCode` **必须存在于本主体科目表**且为末级科目，否则丢弃该建议。
2. AI 返回的金额表达式**只允许引用已知变量**，不允许模型直接给数字总额
   （否则模型改金额，借贷就不平了）。金额一律由系统按模板计算。
3. 生成后**必须过全部校验**（借贷平衡、期间、税前税后一致性）。
4. `confidence < AI_SUGGEST_MIN_CONFIDENCE`（默认 0.75）→ `needsReview = true`。
5. AI 建议**永远不能** `autoPost`，即使 `confidence = 1.0`。

> 第 2 条尤其重要：**绝不让语言模型决定金额**。它只决定"用哪个科目、借贷哪个方向"。

## 6. 自动记账执行流程

```
AutoDraftInvoiceUseCase(invoiceId):

  1. 幂等检查
     key = `INV:${invoiceId}:v${ruleVersion}`
     存在非作废凭证 with idempotencyKey = key → 直接返回（alreadyGenerated=true）

  2. 前置校验
     · invoice.status ∈ {IMPORTED, NEEDS_REVIEW}      否则跳过
     · 所属期间 status == OPEN                        否则拒绝
     · 校验结果无 FAIL                                否则强制人工

  3. 构建上下文 ctx
     { invoice, invoiceLines, partner, contract, entity, period, learned }

  4. L1 规则匹配
     按 (trigger, priority) 顺序遍历启用规则
     逐条求值条件树 → 首个命中即用
     → 渲染 template → DraftVoucherSuggestion(source='RULE')

  5. 未命中 → L2 查询 ClassificationOverride
     → 命中则渲染 → source='LEARNED'

  6. 未命中 → L3 AI
     AI 不可用/超时/低置信 → needsReview = true, source='AI'

  7. 后处理
     · 所有金额 round(2)，重新计算借贷合计
     · 校验 Σdebit == Σcredit（不平 → 抛错，绝不落库）
     · 补齐 partnerId / contractId / invoiceId / 辅助核算维度
     · 组装 reason 字符串（用于凭证备注）

  8. 落库（单事务）
     · 建 JournalVoucher(status=DRAFT, sourceType=INVOICE, idempotencyKey=key,
                        ruleId, ruleReason, confidence)
     · 建 JournalLine[]
     · invoice.status = AUTO_DRAFTED
     · 写 AuditLog

  9. 可选：规则命中统计 rule.hitCount++, lastHitAt
```

### 自动过账（默认关闭，慎用）

`BOOKKEEPING_AUTO_POST=true` **且** 规则 `autoPost=true` **且** 全部条件满足时，才跳过人工：

```
可自动过账的充要条件:
  · 全局开关开启
  · 规则显式标记 autoPost
  · confidence >= 0.98
  · 校验全部 PASS（零 WARNING）
  · 金额 <= 规则配置的 autoPostMaxAmount
  · 该规则历史准确率 >= 99%（基于 ClassificationOverride 与后续纠错统计）
  · 非红字发票
  · 非"无合规票据"场景
```

> 建议：**永远不要打开**。人工点一下「确认」只要 2 秒，
> 而一张错凭证的排查成本是 20 分钟。系统默认 `false`，并在 UI 上解释为什么。

## 8. 规则的可测试性

**每条内置规则必须有一个测试用例**，格式：

```ts
// apps/api/test/rules/purchase-office-supplies.spec.ts
it('专票采购办公用品-未认证', () => {
  const ctx = fixtures.invoice({
    direction: 'INPUT', category: 'SPECIAL_VAT',
    sellerName: '某某办公用品有限公司', sellerTaxNo: '91310000XXXXXXXXXX',
    amountExclTax: '1000.00', taxRate: '0.13', taxAmount: '130.00',
    amountInclTax: '1130.00', itemLines: [{ itemName: 'A4纸' }],
  });
  const r = engine.evaluate(ctx);
  expect(r.source).toBe('RULE');
  expect(r.ruleId).toBe('sys-purchase-office');
  expect(r.lines).toEqual([
    { accountCode: '660202', direction: 'DEBIT',  amount: '1000.00' },
    { accountCode: '22210102', direction: 'DEBIT', amount: '130.00' },
    { accountCode: '2202',   direction: 'CREDIT', amount: '1130.00' },
  ]);
  expect(sumDebit(r.lines).eq(sumCredit(r.lines))).toBe(true);
});
```

再加一个**通用属性测试**（property-based）：对随机生成的票据，
断言「任何规则产出的分录都满足 `Σdebit == Σcredit`」。这条能挡住未来所有规则作者的笔误。

## 9. 规则版本与历史凭证

- `JournalRule.version` 每次修改 +1。
- 幂等键含规则版本：`INV:{invoiceId}:v{ruleVersion}`。
  这意味着**改了规则不会自动重刷已生成的凭证**（这是对的——已入账的账不能悄悄变）。
- 如需重刷：用户显式点「按新规则重新生成」，系统作废旧草稿并生成新的，写审计日志。
- 凭证上永久保留 `ruleId` + `ruleReason` + `ruleVersion`，任何一张凭证都能回答
  「当时为什么这么记的」。

## 10. 与合同、流水的联动

| 联动 | 规则 |
|---|---|
| 发票 ↔ 合同 | 按 `counterpartyId` + 金额区间 + 日期区间自动关联；关联后参与风险比对 |
| 发票 ↔ 流水 | 按 `partnerId` + 金额（允许 ±0.01）+ 日期窗口（±90 天）匹配 → 写 `PaymentAllocation` |
| 多对多核销 | 一次收款对多张发票 → 按到期日先后自动分配，剩余挂预收 |
| 部分核销 | 支持部分金额核销，未核销部分保留在应收/应付 |
| 无法匹配 | 进人工队列，**绝不猜测挂科目** |
