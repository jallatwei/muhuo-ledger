# 03 · 会计内核：凭证 · 期间 · 结账 · 勾稽

> 这一章是整个系统的正确性根基。**领域层代码必须先满足本章的所有不变式。**

## 1. 凭证生命周期（状态机）

```
                ┌──────────────────────────────────────────┐
                │                                          │
   [创建]        ▼                                          │
  MANUAL/自动  DRAFT ──提交审核──▶ REVIEWING ──审核通过──▶ APPROVED ──过账──▶ POSTED
                 │                ▲  │                      │  │              │
                 │                │  │审核不通过             │  │              │红冲
                 │     退回审核───┘  ▼                      │  │              ▼
                 │      (APPROVED→REVIEWING)               │  │           REVERSED
                 │                   VOID ◀────────────────┼──┤     (+ 生成反向 POSTED 凭证)
                 └─────退回制单人─────┴──────────────────────┘  │
                        (APPROVED→DRAFT)                       │
                                                               ▼
                                                             VOID
```

**允许的状态迁移（白名单，超出即报错）**

| From | To | 谁可以做 | 附带动作 |
|---|---|---|---|
| `DRAFT` | `REVIEWING` | OPERATOR/OWNER | — |
| `REVIEWING` | `APPROVED` | OWNER | 记 `reviewedBy/At` |
| `REVIEWING` | `DRAFT` | OWNER | 审核不通过。写入退回理由到 `reviewNote` |
| `APPROVED` | `POSTED` | OWNER | **分配凭证号** + 写余额 + 记 `postedBy/At` |
| `APPROVED` | `REVIEWING` | OWNER | **过账前退回审核**：问题出在审核环节，让审核人重新看 |
| `APPROVED` | `DRAFT` | OWNER | 反审核：单据本身要改，退回制单人 |
| `POSTED` | `REVERSED` | OWNER | 生成红冲凭证（新凭证），原凭证不可改 |
| `DRAFT`/`REVIEWING` | `VOID` | OWNER | 仅未过账可作废；必须填理由 |

**铁律**

1. `POSTED` 之后，凭证的任何字段都不允许 `UPDATE`（只有 `status`、`reversedById` 可变）。要改？红冲重开。
2. **凭证号只在过账时分配**。草稿没有号，避免了"删草稿导致号段空洞"。
3. 凭证号在 `(entityId, voucherWord, periodYear, periodMonth)` 内**从 1 连续无空洞**。
   分配用 `VoucherSequence` 行锁，禁止 `MAX()+1`。

### 凭证号分配（并发安全）

```
BEGIN;
  SELECT next_no FROM voucher_sequence
   WHERE entity_id=$1 AND period_id=$2 AND voucher_word=$3
   FOR UPDATE;                              -- ★ 行锁，串行化同一期间的分配
  -- 不存在则 INSERT ... ON CONFLICT DO NOTHING 后重读
  UPDATE voucher_sequence SET next_no = next_no + 1 WHERE ...;
  UPDATE journal_voucher SET voucher_no=$next, status='POSTED' WHERE id=$voucherId;
COMMIT;
```

### 关于"退回"的三条路径

审核与过账是**两个人、两个时间点**做的事。后一个人发现问题时必须能退回去，
否则流程只能前进不能后退 —— 那会逼着人"将错就错"。

| 路径 | 语义 | 为什么退到这里 |
|---|---|---|
| `REVIEWING → DRAFT` | 审核不通过 | 单据要改，退回制单人 |
| `APPROVED → REVIEWING` | 过账前退回审核 | 审核那步看漏了。**不退到草稿**：账已经审过一次，不该让制单人从头再来，该让审核人重新看 |
| `APPROVED → DRAFT` | 反审核 | 单据本身要改，不只是重审 |

**理由必填且必须回显**。退回是"有后果的动作"（凭证被打回、别人要返工），
留空的退回等于把人卡住却不说原因。所以：
- 理由写入凭证的 `reviewNote`，被退回的人一打开就能看到要改什么
- 同时进审计日志（可追溯是谁、什么时候、因为什么退回）
- 审核通过时清空 `reviewNote`，避免旧理由误导

**`POSTED` 没有任何退回路径**。已过账的账只能红冲 —— 这是"已结账的账改不动"的落点。

**来源状态约束**（实现要点）：
只校验"目标状态是否可达"是不够的。`DRAFT → REVIEWING` 本来就是合法的「提交审核」，
所以"退回审核"这个动作如果只校验目标状态，在草稿上调用时**不会报错**，
反而会静默地把草稿又"提交"了一次。
因此 `assertTransition(to, hint, from)` 要求声明**来源状态** ——
每个动作必须从它语义上该有的状态出发，不靠调用方自觉。

**验证要点**：三条路径各自落到正确状态、理由为空返回 400（不是 500）、
已过账时三条路径全部被拒且状态不变。
## 2. 借贷平衡：四层校验

金额精度：`NUMERIC(18,2)`，最小单位「分」。代码侧统一 `Decimal`，**严禁 `number` 参与金额运算**。

| 层 | 时机 | 校验内容 | 失败处理 |
|---|---|---|---|
| L1 输入 | 前端提交前 | 每行 `amount > 0`；至少 1 借 1 贷；科目为末级且启用 | 表单报错，不提交 |
| L2 领域 | `JournalVoucher.validate()` | `Σdebit == Σcredit`；`Σ > 0`；无重复科目冲突（可选） | 抛 `UnbalancedVoucherError` |
| L3 事务 | 过账事务内、写余额前 | 重新从 DB 读取分录再算一次（防并发篡改） | 回滚 |
| L4 数据库 | 触发器 | `SUM(debit) <> SUM(credit)` → `RAISE EXCEPTION` | 回滚 |

L3 的"重新读一遍再算"看似多余，实际拦住了一类真实事故：**草稿期间被人改过金额，而内存对象还是旧的**。

## 3. 会计期间

### 状态机

```
OPEN ──开始结账──▶ CLOSING ──结账成功──▶ CLOSED
  ▲                   │                    │
  │                   │失败(回滚)           │反结账(需 OWNER + 理由)
  └───────────────────┴────────────────────┘
```

- `OPEN`：可增删改凭证。
- `CLOSING`：**禁止**任何凭证写入（施工中）；允许结账流程自己生成的结转凭证（内部标记放行）。
- `CLOSED`：完全冻结。触发器拒绝写入。

### 期初状态

新建主体时自动创建当年 12 个期间，全部 `OPEN`，`AccountBalance` 为空。
第一个期间的期初余额来源二选一：

1. **全新启用**（新公司）：期初全 0。
2. **中途启用**（已有账套）：用户通过「期初余额录入」界面导入，系统生成一张特殊凭证
    `voucherWord='年初'`, `voucherNo=0`, `sourceType=OPENING`，借贷合计必须相等才允许保存。
   期后所有期间通过 `rollForwardBalances()` 自动滚动。

## 4. 余额计算逻辑（唯一权威公式）

对每个末级科目 `a`、每个期间 `p`：

```
借方科目（direction = DEBIT）:
  closingDebit  = openingDebit  + debitOccurred  − creditOccurred
  closingCredit = 0
贷方科目（direction = CREDIT）:
  closingCredit = openingCredit + creditOccurred − debitOccurred
  closingDebit  = 0
其中（允许为负，表示反向余额，如银行存款透支）:
  openingDebit(p)  = closingDebit(p−1)
  openingCredit(p) = closingCredit(p−1)
  p 为年度首期时，取自「年初」凭证或上年 12 月期末
```

发生额直接聚合已过账凭证：

```sql
SELECT account_id,
       SUM(CASE WHEN direction='DEBIT'  THEN amount ELSE 0 END) AS debit_occ,
       SUM(CASE WHEN direction='CREDIT' THEN amount ELSE 0 END) AS credit_occ
FROM journal_line
WHERE entity_id = $1 AND period_id = $2
  AND voucher_id IN (SELECT id FROM journal_voucher WHERE status IN ('POSTED','REVERSED'))
GROUP BY account_id;
```

> **红冲的处理**：被红冲的原凭证状态为 `REVERSED`，但它的分录**依然计入发生额**——
> 因为红冲凭证本身也过账了，两者相加净额为 0。若把 `REVERSED` 排除，就会出现"冲销了但原账还在"的灾难。
> 这正是很多自制记账工具翻车的地方。

### ★ 余额同步时机（实现约束）

余额表由 `bk_rebuild_balances(entity_id, period_id)` **幂等重算**：先删该期间余额，
再由凭证重新聚合 → 按科目方向计算期末 → 滚动下期期初。

余额表必须与凭证保持一致，否则报表和明细账会对不上，而且**中间没有任何报错** ——
这是最危险的一类静默错误。因此必须在下列时机同步：

| 时机 | 动作 | 位置 |
|---|---|---|
| **凭证过账** | 在同一事务内重算该期间余额 | `VoucherService.post()` |
| **凭证红冲** | 同上（原凭证状态变化，余额需刷新） | `VoucherService.reverse()` |
| 结账步骤 S7 | 重算并冻结本期余额 | 月结流程 |
| 用户主动「账务自检 → 重算余额」 | 手动触发（幂等，安全） | `/accounting/rebuild-balances` |

**为什么放在过账事务内**：事务回滚时余额一并回滚，不会出现「凭证没进但余额进了」。
重算是幂等的（先删后算），重复过账不会累积误差。

**为什么不放在数据库触发器里**：一次重算要处理该主体全部末级科目（约 123 个），
放在触发器里会让批量过账退化成 O(n²)。放在服务层的过账事务内，
既保证一致性，又能在批量场景下由调用方控制节奏。

> 这个缺口是端到端验证抓出来的：过账后 I4 立刻不成立。**I4 的价值正在于此** ——
> 它把「余额表与凭证脱节」这种静默错误变成了一个显式的失败断言。

### 全局勾稽不变式（可随时自检）

| 不变式 | 检查 SQL 思路 | 违反含义 |
|---|---|---|
| I1 全部凭证借贷平衡 | 恒由 L4 触发器保证 | 数据损坏 |
| I2 全部科目借方余额合计 == 贷方余额合计 | `SUM(closing_debit) == SUM(closing_credit)` | 余额表被污染 |
| I3 上期期末 == 本期期初 | 逐科目比对 | 滚动出错 |
| I4 本期发生额 == 该期凭证分录聚合 | 重算比对 | 余额表与凭证不一致 |
| I5 凭证号连续无空洞 | `MIN=1 且 COUNT=DISTINCT 且 MAX=COUNT` | 号段被破坏 |

系统提供「账务自检」按钮，一次性跑完 I2~I5 并给出可一键修复（`rebuildBalances`）的选项。

## 5. 月末结账

### 5.1 结账检查清单

`BLOCKER` 不通过 → **不允许结账**；`WARNING` → 提示但可强制（需填理由）；`INFO` → 仅展示。

| # | code | 级别 | 检查内容 | 修复入口 |
|---|---|---|---|---|
| 1 | `DRAFT_VOUCHERS` | BLOCKER | 本期存在 `DRAFT`/`REVIEWING` 凭证 | 去审核 |
| 2 | `UNPOSTED_VOUCHERS` | BLOCKER | 本期存在 `APPROVED` 未过账凭证 | 去过账 |
| 3 | `PENDING_INVOICES` | BLOCKER | 本期有 `IMPORTED`/`AUTO_DRAFTED`/`NEEDS_REVIEW` 发票 | 去入账 |
| 4 | `UNCERTIFIED_INPUT` | WARNING | 本期进项专票未全部勾选认证 | 去认证 |
| 5 | `UNMATCHED_INVOICE_TAX` | WARNING | 已入账发票税额 ≠ 凭证税额合计 | 查差异 |
| 6 | `BANK_UNRECONCILED` | WARNING | 本期银行流水存在 `UNMATCHED` | 去匹配 |
| 7 | `VOUCHER_NO_GAP` | BLOCKER | 凭证号不连续（不变式 I5） | 自检修复 |
| 8 | `BALANCE_INVARIANT` | BLOCKER | 不变式 I2/I3/I4 任一不通过 | 重算余额 |
| 9 | `AUX_MISSING` | WARNING | 要求辅助核算的科目缺维度 | 补维度 |
| 10 | `CASH_NEGATIVE` | WARNING | 库存现金/银行存款出现贷方余额 | 查漏记收入 |
| 11 | `RISK_ALERTS_OPEN` | WARNING | 本期存在未处理的 `CRITICAL` 风险 | 去风险页 |
| 12 | `PERIOD_DATE_MISMATCH` | BLOCKER | 有凭证日期落在本期之外却挂在本期 | 修正期间 |

### 5.2 结账步骤（可断点续跑）

`PeriodCloseRun.steps` 记录每一步状态，失败后修复数据可继续，不必从头再来。

| 步 | 动作 | 生成凭证 | 幂等键 |
|---|---|---|---|
| S0 | 跑检查清单 | — | — |
| S1 | 增值税归集：按 `taxTag` 汇总本期销项/进项，生成 `VatPeriodAggregate` | — | `VATAGG:{periodId}` |
| S2 | 进项税额结转：已认证的「待认证进项税额」→「进项税额」 | 有 | `VAT-CERT-TRANSFER:{periodId}` |
| S3 | 转出未交增值税：`应交增值税` 贷方余额 → `未交增值税` | 有 | `VAT-TRANSFER:{periodId}` |
| S4 | 计提附加税费：以 S3 的应交增值税为基数 × (城建+教育+地方教育) × 减免 | 有 | `SURTAX:{periodId}` |
| S5 | 结转损益：将所有 `PROFIT_LOSS` 类科目余额结转到 `本年利润` | 有 | `PL-CARRY:{periodId}` |
| S6 | 计提企业所得税：按利润总额 × 适用税率（小微优惠） | 有 | `CIT:{periodId}` |
| S7 | 重算并冻结本期余额 | — | — |
| S8 | 生成法定报表快照（资产负债表/利润表/现金流量表） | — | `REPORT:{periodId}` |
| S9 | 期间置 `CLOSED`，滚动下期期初 | — | — |
| S10 | 生成当期风险扫描结果 | — | — |

**每一步都幂等**：先按幂等键查是否已存在，已存在则跳过（并可选择"重建"）。
这让"结账失败 → 修数据 → 重跑"变成安全操作。

### 5.4 反结账（必须显式且留痕）

```
反结账(periodId, reason):
  1. 校验权限 = OWNER，reason 非空
  2. 校验该期间的 TaxFiling 未标记 FILED（已申报则禁止反结账）
  3. 删除 S1~S8 生成的结转凭证（红冲而非物理删除，保留痕迹）
  4. period.status = OPEN; reopenedCount += 1
  5. 重算余额
  6. 写 AuditLog(action='REOPEN', reason)
```

**已申报的期间不允许反结账**——这条硬约束防止"账和申报表对不上"。

## 6. 年结（12 月结账之后）

1. 12 月正常月结。
2. 年度损益已全部进入 `本年利润`。
3. 将 `本年利润` 转入 `利润分配—未分配利润`：

```
借：本年利润                    XXX
    贷：利润分配—未分配利润                XXX     （盈利）
或反向（亏损）
```

4. 按章程计提盈余公积（可选，手动或规则）：

```
借：利润分配—提取法定盈余公积      XXX
    贷：盈余公积—法定盈余公积              XXX
```

5. 生成次年 1 月的「年初」凭证（`voucherNo=0`）作为新年度的期初。
6. `FiscalYear.status = CLOSED`。

## 8. 账本与报表

| 输出 | 数据来源 | 备注 |
|---|---|---|
| 科目余额表 | `AccountBalance` | 期初/本期发生/期末，按科目层级汇总 |
| 总账 | `AccountBalance` 逐期 | 每个科目的逐月发生与余额 |
| 明细账（三栏式） | `JournalLine` join `JournalVoucher` | 按科目+期间，含凭证号/日期/摘要/对方科目 |
| 多栏明细账 | `JournalLine` 按对方科目透视 | 管理费用、应交税费最常用 |
| 辅助账 | `JournalLine` 按 `partnerId`/`auxProject` | 往来对账单 |
| 资产负债表 | `AccountBalance` → `AccountMapping` | 见 06 章 |
| 利润表 | 本期 + 本年累计发生额 | |
| 现金流量表 | 主表：`cashflowTag` 直接法归集；附表：间接法由净利润倒推 | 第一版**直接法**为主 |

### 报表平衡校验（结账前必跑）

```
资产负债表：Σ资产期末 == Σ(负债 + 所有者权益)期末
利润表：净利润 == 本年利润本期发生额（结账后）
       本年累计净利润 == 本年利润余额
现金流量表：期末现金 == 资产负债表「货币资金」期末
```

这三条对不上，报表就是错的，**绝不输出**。

## 9. 错误与异常处理约定

| 场景 | 行为 |
|---|---|
| 借贷不平 | 抛 `UnbalancedVoucherError`，UI 高亮差额，**不落库** |
| 期间已关闭 | 抛 `PeriodLockedError`，提示"该期间已结账，请先反结账" |
| 重复入账（幂等键冲突） | 返回已存在的凭证，标记 `alreadyGenerated: true`，**不报错** |
| 非末级科目记账 | 抛 `NonLeafAccountError` |
| 金额精度超 2 位 | 抛 `AmountPrecisionError`（不做静默四舍五入） |
| 凭证号耗尽（>9999） | 允许继续到 5 位，但 UI 提示（小企业不会遇到） |
| AI 识图失败 | 单据置 `FAILED`，进人工录入队列，**不阻塞**其他单据 |

### 错误信息的呈现约定（实现约束）

所有异常经统一过滤器（``apps/api/src/common/filters/all-exceptions.filter.ts``）翻译为：

``````json
{
  "statusCode": 400,
  "code": "BK_E_UNBALANCED",
  "message": "内部技术信息",
  "userMessage": "记-（未编号）借贷不平：借方合计 1000.00，贷方合计 900.00，差额 100.00。凭证未保存。"
}
``````

- 前端**只展示 ``userMessage``**。
- 领域层错误（``DomainError``）本身就带 ``userMessage``，直接透传。
- **数据库触发器抛出的 ``BK_E_*`` 错误同样被翻译**，因此「应用层拦截」与「数据库层拦截」
  对用户是同一套提示 —— 用户不需要知道是哪一层拦的。
- 未预期的异常返回统一话术并说明「数据未被修改，请重试」，避免用户误以为账已经乱了。
