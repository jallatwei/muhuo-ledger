# 木火账房（Bookkeeper）

面向**个人与小组织**的自动记账工具。导入合同、发票（含银行流水/回单），系统自动完成账务整理、生成记账凭证；月底结账后一键生成**可打印的当月凭证册**，并按税务申报口径输出**财务报表与纳税申报表**。

- 会计准则：**《小企业会计准则》**
- 纳税人身份：**一般纳税人**（第一版）
- 合同定位：**辅助/备查**，实际记账依据为**发票 + 银行流水**
- 识图：云端多模态大模型 API 为主，Provider 可替换（含本地/离线 Mock）
- 部署：本地 Docker 开发 → 云端 Docker 部署，**开发环境与软件本体严格分离**

> 设计原则一句话：**宁可少记，不可记错。** 所有自动化产出都进「待确认」区，人审核后才入账。

**名字的来历**：「木火」取自界面配色的依据 —— 日主丙火生于丑月（腊月）天寒地冻，
非木不生，木为用神、火为喜神；「账房」是旧时管账之处。
产品名与实际配色可互相印证：打开界面看到的主色是松绿（木），辅色是赤陶（火）。
名字与说明集中在 packages/shared/src/brand.ts，改一次全局生效
（登录页品牌区、侧边栏 Logo、页面标题、凭证册页脚、API 启动横幅同源）。

### 为什么 `docker/` 和 `apps/` 分开

软件本体只认**环境变量**（`DATABASE_URL`、`AI_PROVIDER`、`TZ`…），不知道自己在哪跑。
`docker/` 只负责「怎么把它跑起来」。换云厂商 = 换一个 compose 文件，改代码的零行。

## 快速开始（本地开发）

```bash
# 1. 准备环境变量
cp deploy/env/.env.dev.example deploy/env/.env.dev

# 2. 起本地开发栈（PostgreSQL + API 热重载 + Web 热重载）
docker compose -f docker/dev/docker-compose.yml --env-file deploy/env/.env.dev up -d

# 3. 首次初始化：建表 + 灌入小企业会计准则科目表
docker compose -f docker/dev/docker-compose.yml exec api pnpm --filter @bookkeeper/api prisma:deploy
docker compose -f docker/dev/docker-compose.yml exec api pnpm --filter @bookkeeper/api seed

# 4. 打开
#    Web:      http://localhost:5173
#    API:      http://localhost:3000/api
#    Swagger:  http://localhost:3000/api/docs
#    DB:       localhost:5433  (bookkeeper / bookkeeper_dev_pwd)
```

开发模式下 `AI_PROVIDER=mock`，识图返回固定样例数据，**不消耗任何 API 额度**也能把全链路跑通。

### 只用本机 Node 跑（不起应用容器，只借容器的数据库）

```bash
docker compose -f docker/dev/docker-compose.yml --env-file deploy/env/.env.dev up -d postgres
pwsh -File tools/setup-api-env.ps1          # 生成 apps/api/.env（主机名改为 localhost:5433）

pnpm install
pnpm --filter @bookkeeper/shared build
pnpm --filter @bookkeeper/api exec prisma generate
pnpm --filter @bookkeeper/api exec prisma migrate deploy

pnpm --filter @bookkeeper/web dev                                    # Web → :5173
pwsh -File tools/e2e-verify.ps1                                      # 验证 36 项防线
```

## 核心链路

「录入凭证」下有两个入口，对应两条完全不同的下游路径：

```
                    ┌── 手工录入  /vouchers/new
  录入凭证 ─────────┤
                    └── 识别录入  /vouchers/recognition
                              │
        ┌─────────────────────┴─────────────────────┐
        │ 单据类                                     │ 报表类
        │ 发票 · 银行回单 · 银行流水                  │ 资产负债表 · 利润表 · 纳税申报表
        ▼                                            ▼
   [1] 文件摄入                                  [1] 文件摄入
       图片→视觉识别                                 图片→视觉识别
       PDF→优先文本层（更准更省）                     PDF→优先文本层
       Excel/CSV→逐单元格精确读取                     Excel/CSV→逐单元格精确读取 ★零误差
        │                                            │
   [2] 抽取 → 结构化 JSON                        [2] 抽取 → 保留原始行项目
        │                                            │
   [3] 会计交叉校验 V1–V12                       [3] 平衡与勾稽校验
       金额勾稽 · 税率 · 购销方方向                  资产 = 负债 + 权益（★只报告不修正）
        │                                            │
   [4] 路由决策                                   [4] 建档（仅存档，不入账）
       校验通过+置信度足够 → 待确认凭证               余额与合计供期初建账取数
       否则 → 强制人工复核                            │
        │                                            │
   [5] 人工确认 → 过账 → 影响账簿                 ✗ 不生成任何凭证
        │
   [6] 月结 → 认证归集→转出未交→结转损益→所得税→锁期
        │
   [7] 输出：月末一次打印 A4 凭证册（凭证 + 发票原件同册）
        │
   [8] 税务填报：月度出财务报表 + 增值税及附加底稿
                季度末月加所得税预缴、12 月加年度汇算底稿
                （★ 出底稿，不申报；判断项留空）
        │
   [9] 辅助：每月检索官方政策变动（只呈现原文与日期，不判适用性）
             报销自检（机械核查 + 风险提示，非税务意见）
```

**为什么报表类绝不生成凭证**：报表是"结果"，凭证是"原因"。
拿资产负债表的期末数去生成凭证，会把明细账里已有的资产再确认一遍 —— 资产凭空翻倍。
报表的唯一用途是**为期初建账提供真实数据**，由重建流程去取用。

## 界面主题

配色与 Logo **依八字喜用而定**，完整推算与色彩依据见
[`docs/主题配色-八字喜用.md`](docs/主题配色-八字喜用.md)，
推算口径与文献出处见 [`docs/八字推算-口径与依据.md`](docs/八字推算-口径与依据.md)。

命局：**甲子年 丁丑月 丙寅日 戊子时** —— 日主**丙火**生于丑月（腊月）天寒地冻，
年支子、时支子冬水本旺，日支寅藏甲木是全局唯一的生火之源，
属**寒火向阳、非木不生**之象。用神木、喜神火、闲神土、忌神水金。

> ★ 本页曾记为「甲子日、日主甲木」并把火定为用神。核对儒略日后
> JDN(1985-01-27) = **2446093**（原记为 2446097，差 4 天），日柱应为**丙寅**，
> 时柱随之由甲子更正为**戊子**。喜用整体改变，主色系从「火土」改为「**木火**」。
> 更正过程与教训见主题配色文档附录。

### 配色策略：低饱和 · 商用质感

| 原则 | 做法 |
|---|---|
| **骨架中性** | 中性色取**近真灰**（饱和 ≤8%），不带色相。界面主体必须"无色"，否则整屏泛棕泛黄立刻显旧 |
| **颜色克制** | 主色（木）30%、辅色（火）24%、点缀（土）20%，全板强调色饱和 ≤ 31% |
| **色相承载五行** | 五行意象由色相表达，不由饱和度堆：木 156° 松绿 / 火 14° 赤陶 / 土 48° 赭黄 |
| **色相与判定对齐** | 色板的色相区间必须落在 `hueToElement()` 的判定区间内，否则"这个色属于木"和占比统计会自相矛盾。`build-palette.mjs` 里有一条专门校验这个 |
| **可读性优先** | 所有承载文字的色均过 WCAG AA（≥4.5:1），由 `tools/build-palette.mjs` 校验 |

| 令牌 | 色值 | 饱和 | 色相 | 五行 | 用途 |
|---|---|---|---|---|---|
| `--bk-wood-500` | `#376754` | 30% | 156° | 木·**用神** | **主色**：主按钮、选中态 |
| `--bk-fire-500` | `#966a5c` | 24% | 14° | 火·喜神 | 辅色：次级强调 |
| `--bk-earth-500` | `#847b58` | 20% | 48° | 土·闲神 | 点缀：警告 UI 元素 |
| `--bk-ink` | `#2a2a2d` | 3% | — | 中性 | 正文 |
| `--bk-aside-bg` | `#252528` | 4% | — | 中性 | 侧边栏底 |
| `--bk-debit` | `#946157` | 26% | 10° | 火 | 借方金额 |
| `--bk-credit` | `#34604e` | 30% | 155° | 木 | 贷方金额 |

关键改动：借方金额原为**蓝色**（属水，忌神方位色）改为火红；侧边栏原为**深蓝黑**改为近真灰深色；
主色由饱和 70% 降到 30%。

> **变量名刻意不改**：`--bk-wood-*` / `--bk-fire-*` 表达的是"这条色阶属于哪个五行"，
> 不是"谁是主色"。改喜用只换哪条色阶当主色，变量名保持不变 ——
> 前端有 360 多处引用这些变量，为改角色去重命名只会引入大量无谓风险。

**Logo**（`apps/web/src/components/AppLogo.vue`）取**木火相生**之象，
构图随更正后的喜用颠倒：**树为主，火在根部温养** ——
低饱和松绿主干与枝叶（木·用神）→ 贴地一簇低饱和赤陶焰（火·喜神）→
赭黄地面与近真灰外廓（土）承托，三点极淡青灰如实承认冬水本旺但不给主角位置。
颜色走 CSS 变量，改主色时 Logo 跟着变。

### 外观偏好页：实控人八字

`/appearance` 不是普通取色器 —— 页面顶部先让人把**出生信息**填对，
算出四柱与喜用，最后才轮到调色（**配色是喜用的结果**）。

- **输入**：公历/农历（含闰月）· 出生日期时刻 · 出生地（62 个地级市预置 + 手工填经纬度）·
  真太阳时开关 · 子时日界两派
- **真太阳时明细**分开列：经度时差 / 均时差 / 夏令时补偿 / 合计。
  把 `+14 分` 是怎么来的摆出来，用户才能判断"为什么这里算的和我手机上那个 App 不一样"
- **四柱 + 十神**、五行本气分布（悬停看含藏干加权值）
- **边界警示**：离节气或时辰边界近时明确标出距离（默认示例距子时边界 32 分钟）
- **另一种子时口径的结果**、**推算口径与依据**（可折叠，逐步列出怎么算的）

### 全局偏好（可持久化）

配色不是硬编码，而是可调整、跨会话生效的**全局偏好**。

- **存储**：`SystemConfig` 表，key = `ui.theme`
- **层级**：主体级配置 → 全局配置 → 内置默认（因为界面偏好是"人的"而非"账套的"）
- **缓存**：localStorage 先于网络请求应用（避免刷新闪默认色），后端为准覆盖
- **接口**：`GET/PATCH /api/preferences/theme`、`GET /api/preferences/theme/tokens`、`POST .../reset`
- **五行分析**：统计木火令牌占比，并**逐令牌校验实际色相**是否偏离应有五行 ——
  把蓝色填进 `wood500` 会被直接指出来
- **调色方向由喜忌表推导**：告警与结论的措辞全部来自 `ELEMENT_ROLE`，
  不硬写"火土"。硬写的话改一次喜用必然漏掉某处，而漏掉的那处会继续给错误建议

## 电子发票仓库与凭证勾稽

```
Document（原始文件）──1:1──▶ Invoice（结构化发票）──N:M──▶ JournalLine（凭证分录）
     │                                                            │
     └──────────── DocumentLink(ATTACHMENT) ──────────────────────┘
                    显式挂接的附件（凭证册据此带出）
```

仓库不额外建表 —— 它的价值在于「能查到」与「能打出来」，而这两件事都依赖与凭证的勾稽关系。
单独再建一张"仓库表"只会产生同步问题。

### 附件的三条关联路径（按可靠性排序）

| 路径 | 说明 |
|---|---|
| `JournalLine.invoiceId → Invoice.documentId` | 最强关联。自动记账生成的凭证走这条，分录行直接指向发票 |
| `DocumentLink(VOUCHER → DOCUMENT, ATTACHMENT)` | 显式挂接。人工把单据作为附件挂到凭证上 |
| 两者都没有 | 打印时标注「本凭证未关联原始单据」，不静默漏掉 |

三者去重合并。同一张发票被多行引用时只打印一次。

### 导入单据：两步走

仓库页右上角「导入单据」，或列表里对某一份点「识别」。

```
① 上传入库   POST /api/documents/upload          无损 · 幂等 · 必成
             文件按内容哈希去重，同一份文件传两次只存一份
                    ↓
② 识别落库   POST /api/documents/:id/recognize   有损 · 要花钱 · 可能被拒
             抽取 → 会计交叉校验 → 落为发票台账 + 建立原件关联
```

**为什么必须分成两步，而不是"上传即识别"：**

| 理由 | 说明 |
|---|---|
| 入库无损、识别有损 | 先保证原件一定存住。识别失败、被拒、模型抽风，原件都在库里，随时可重试 |
| 识别要花钱 | 真实模型按 token 计费。一次拖 30 张票进来，未必都想立刻识别 |
| 校验必须前置 | 识别结果只有**校验通过**才允许落库 |

### 什么情况下拒绝落库

| 校验 | 行为 | 为什么 |
|---|---|---|
| 金额勾稽不成立（不含税+税额 ≠ 价税合计） | **拒绝**，`force` 也绕不过 | 这是数据完整性约束，不是识别质量问题。坏数据进台账会污染进项抵扣统计 |
| 方向无法判定（购销双方都不是本主体、模型也没给） | **拒绝**，`force` 也绕不过 | 方向猜错 = 进项票被记成销项 = 虚增收入和销项税。事实缺失不能靠"猜"补 |
| 票面其他字段可疑（税率、号码格式、卖方不在档案…） | 落库，但给出告警与待核对项 | 这些是"值得看一眼"，不是"一定错" |
| 方向取自模型但票面无从交叉验证 | 落库，同时把疑点写进 `reviewNote` | 不静默 —— 复核时能看当初为什么这么判 |

**被拒之后原件不会丢**：文件已入库，列表里点「识别」可随时重试；也可在原表修正后重新上传。

### 方向判定：身份比对优先于模型

```
① 用本主体的名称/税号去比对购买方与销售方   ← 硬事实，最可靠
② 用模型给出的 direction                    ← 有事实支撑时采纳；无支撑则记疑点
③ 两者都没有 → 拒绝并要人工指定               ← 绝不猜
```

原先的实现是 `direction === 'OUTPUT' ? 'OUTPUT' : 'INPUT'` —— 一个静默兜底。
模型返回 `null` 时它会**默默记成进项**。这类默认值就是记错账的典型来源：
票面上明明看不清方向，台账里却出现一个看起来很确定的"进项"。

## 凭证册打印（A4）

**日常不打印，月末结账后一次性打一本。**

| 册内结构 | 内容 |
|---|---|
| 封面 | 主体名称、统一社会信用代码、期间、凭证号范围、张数、附件数、四联签字位 |
| 记账凭证页 | 科目编码/名称/摘要/借方/贷方，合计行附**中文大写金额**，制单·审核·记账签字位，命中规则依据 |
| 发票原件页 | 每张凭证自动附上它关联的发票原件（图片内联为 data URL，打印不会丢图） |
| 册末汇总 | 科目发生额汇总表，借贷双方合计相等验证 |

**版式约定**

- A4 纵向；左侧 25mm 装订边（`@page` 提供页边距，`.page` 自身在打印时尺寸清零，避免每节占一页半）
- 金额等宽字体、右对齐、千分位、两位小数 —— 会计核对的硬要求
- 每张凭证独立成页，表格不跨页断开
- 未结账期间允许打印，但封面与页首显著标注「凭证仍可能变动」
- `attachmentMode`：`NONE` 仅凭证 / `IMAGE` 凭证+图片附件（推荐）/ `ALL` 全部附件（PDF 类会留提示页）

**为什么返回 HTML 而不是直接生成 PDF**

1. 浏览器 `window.print()` 的排版保真度与打印驱动配合最好，且零额外依赖
2. 同一份 HTML 直接用于屏幕预览，避免「屏幕一套、打印另一套」
3. 后续要出 PDF 时，用 Puppeteer 渲染同一份 HTML 即可，业务代码不变

## 历史数据导入

场景：以前没有账（或账已丢失），只有**销项开票明细 + 已勾稽进项发票 + 税务申报记录**，
外加（如果有的话）**代账公司出的财务报表**。

> ★ 如果你手上有代账公司的资产负债表，**先做这件事**：
> 到「录入凭证 → 识别录入」选「资产负债表」，传原始 Excel，确认并建档。
> 它会让下面"推不出来"的那一列里的大部分科目直接变成"有据"，
> 不必再靠倒轧 —— 这是提升历史建账质量最划算的一步。

### 核心约束 —— 说清楚哪些数字是"有据"的

从这三类数据里**能算准**的科目是有限的：

| 能算准（有据） | 推不出来（必须问人或倒轧） | 有已建档报表时 |
|---|---|---|
| 主营业务收入（申报表 / 发票聚合） | **现金与银行存款余额**（没有任何支付流水） | ✅ 取「货币资金」行 |
| 销项税额、进项税额、已勾稽税额 | 无票成本费用（只有税表利润总额能反推总额） | — 仍需倒轧 |
| 应交增值税（申报表期末未缴） | 存货、固定资产（发票口径分不清"已耗用"与"结存"） | ✅ 取对应行 |
| 应交企业所得税、税金及附加 | 实收资本、股东借款 | ✅ 取「实收资本」行 |
| 应收账款（销项价税合计为上限） | 预收/预付、其他应收应付 | ✅ 取对应行 |
| 累计未分配利润（Σ各年净利润） | | ✅ 取「未分配利润」行，并与倒轧值对比 |

因此产出的是**期初建账方案**，每一行都强制标明来源：

```
DECLARED  申报表 / 已建档财务报表直接取数（最可信）
INVOICE   发票明细聚合（可信）
DERIVED   由会计恒等式倒轧（推算，需人工确认）
MANUAL    人工补录
```

- **DERIVED 行一律标记 needsReview**，不会伪装成事实
- 未分配利润那一行同时显示「按净利润累计的真实值」与「数据缺口」，并说明缺口来自哪些未录入的科目
- 差额由未分配利润归位（恒等式要求），但会显式提示「账能平，但资产负债表是错的」
- 全流程唯一的写账动作是最后一步「确认方案 → 生成期初凭证」，且必须人工确认

### 接口流程

| 步骤 | 接口 | 说明 |
|---|---|---|
| 1 | `POST /api/history/preview` | 上传文件 → 解析 + 列名映射（**不落库**） |
| 2 | `POST /api/history/import` | 确认映射后落库（发票按方向+代码+号码去重） |
| 3 | `POST /api/history/reconstruct` | 年度重建：发票↔申报核对、成本倒轧、无票成本识别 |
| 4 | `POST /api/history/proposal` | 生成期初建账方案 |
| 5 | `POST /api/history/proposal/:id/adjust` | 逐行调整（改金额或删行） |
| 6 | `POST /api/history/proposal/:id/confirm` | ★ 确认后生成期初凭证（「年初」字 + 0 号） |

## 识别录入

位置：**录入凭证 → 识别录入**（`/vouchers/recognition`）。
在「手工录入」页右上角也有一个跳转按钮，录到一半想改成识别可以直接过去。

这个页面承担**两类识别**，它们共用同一套"文件摄入 → 抽取 → 校验"骨架，
但从校验开始就分道扬镳，因为下游完全不同。

### 一、文件是怎么被读进来的（直接决定识别准不准）

| 文件类型 | 处理路径 | 为什么 |
|---|---|---|
| 图片 png/jpg/webp/bmp | base64 → 多模态视觉识别 | 只有像素，没有别的选择 |
| PDF | **优先取文本层**（`pdf-parse`） | 电子发票/电子报表的文本层是机器生成的，比"看图"更准，token 也更省 |
| PDF（扫描件） | 无文本层时转视觉识别，并明确提示 | 扫描件没有可选路径，但必须让用户知道金额要重点核对 |
| Excel xlsx | **逐单元格精确读取** | 财报多来自代账公司的 Excel。渲染成图片再让模型看，等于把精确数据主动降级成有损识别 |
| CSV / TSV | 逐字段解析（RFC4180 引号转义） | 税局导出常见制表符分隔；首行常是标题，不能只看首行判分隔符 |

界面会把"文件读取方式"和**模型实际读到的内容**一并展示出来 ——
识别错了，第一件事就是看模型到底看见了什么，而不是猜。

> ⚠️ 财务报表强烈建议直接传原始的 Excel，不要打印或扫描。
> 扫描件会引入 OCR 误差，而报表里一个数字错了，整张资产负债表就平不了。

### 二、单据类：发票 / 银行回单 / 银行流水

识别 → 会计交叉校验（V1–V12）→ 路由决策：

- 校验全部通过且置信度 ≥ 阈值 → 可生成**待确认凭证**（仍需人工确认后才过账）
- 任一项 FAIL → **强制人工复核，且不允许一键确认绕过**
- `BOOKKEEPING_AUTO_POST` 默认 `false`：AI 永远不能直接把账做掉

其中 V4（购销方方向）是最关键的一条：方向搞反会让进项票被记成销项，虚增收入和销项税。

### 三、报表类：资产负债表 / 利润表 / 纳税申报表

**只建档，不生成凭证。** 三条硬规则：

1. **保留原始行项目，不强行映射科目。**
   不同年度、不同地区、不同软件导出的报表行次都有差异。
   先把"表上写了什么"如实存下来 —— 这是不会错的做法；映射留到重建阶段按需做。

2. **平衡自检只报告、不修正。**
   资产 ≠ 负债 + 权益时，如实记录差额并告警。
   擅自"修正"有可能把真实数据改成错的（也许是我们理解错了行次含义）。
   存档时若报表不平，会弹窗要求人工确认，并把差额写进档案备注。

3. **不做自动重算。**
   若"资产总计"与明细之和对不上，记录差额并告警，**不擅自改数**。

### 四、接口

| 接口 | 说明 |
|---|---|
| `GET /api/ai/targets` | 6 类识别目标清单（含中文名与适用说明） |
| `POST /api/ai/recognize` | ★ 上传文件识别（multipart），返回「文件读取方式 + 抽取结果 + 校验结论」 |
| `POST /api/ai/extract` | 用内置样例跑识别（开发与验证用，不消耗额度） |
| `POST /api/history/statements` | 保存报表 / 申报表档案（幂等：同主体+同类型+同报表日期 → 覆盖） |
| `GET /api/history/statements` | 已建档的财务报表清单 |
| `DELETE /api/history/statements/:id` | 删除报表档案（识别错了要能撤销） |
| `GET /api/history/filings` | 已建档的申报记录清单 |

识别结果落入两张表：

- `financial_statement_record` —— 资产负债表 / 利润表 / 现金流量表（行项目存 JSONB）
- `history_filing_record` —— 增值税 / 企业所得税申报记录（销售额、销项、进项、应纳税额、附加税费）

### 五、★ 建档之后：报表怎么真正被用上

只把报表存起来没有意义。系统把已建档的资产负债表**自动接进期初建账方案**：

- 取数优先级：**已建档报表 > 人工输入 > 倒轧**
  （报表是别人（代账公司/税局）出的表，人工输入是"我记得大概是这个数"）
- 映射规则：报表行项目 → 科目，**只映射能唯一对应一个科目的行**
- `GET /api/history/declared-statements` 返回映射明细，界面直接展示
  "哪些行用上了、哪些行被跳过、为什么"

**合计行一个都不映射。**「流动资产合计」「资产总计」「负债合计」这些行如果被映射到科目，
会让资产被重复确认（明细账里已经有一遍）。这一条有专门的测试守着。

**「应交税费」也不映射。** 报表上只有一行，无法确定它是未交增值税还是应交企业所得税——
这是会计判断而不是识别问题，且没有唯一答案。期初税额本来就以申报表为准，那里更准。

带来的实际差别（用验证脚本的真实数字）：

| | 没有报表 | 有报表 |
|---|---|---|
| 货币资金 | 倒轧（凑数科目，失真最大） | **386,400.00**，取自报表 |
| 存货 | 要求人工补录 | **420,000.00**，取自报表 |
| 固定资产 / 累计折旧 | 要求人工补录 | **280,000.00 / 63,000.00**（贷方） |
| 实收资本 | 要求人工补录 | **500,000.00**，取自报表 |
| 待补录清单 | 5 项 | **0 项** |
| 现金口径 | `DERIVED`（倒轧） | `DECLARED`（有据） |

一个容易踩的坑：`减：累计折旧` 曾被误判成"合计行"整行丢掉 ——
那会让固定资产净值虚高整整一个折旧额。报表里的「减：」「加：」只是列示前缀，
指向的是独立科目，不是合计行。

### 六、识别结果的可追溯性

每次识别都会写 `ai_call_log`：promptKey、promptVersion、模型、token 用量、耗时、原始响应。
任何一张凭证、任何一份报表档案，都能反查到"当时 AI 说了什么"。

### 七、验证

```bash
pwsh -File tools/verify-recognition.ps1   # 63 项
```

覆盖的关键行为：

| 组 | 验证内容 |
|---|---|
| 1 | 识别目标清单正确（6 类，报表类被正确分组） |
| 2 | CSV 引号转义（`"215,000.00"` 不被拆列） |
| 3 | 制表符分隔文件的探测（不再只看首行） |
| 4 | ★ 不平衡报表只报告不修正（差额 120000 原样保留） |
| 5–6 | 建档 + **幂等**（同一份报表重复上传是覆盖而非新增） |
| 7 | 不平衡报表建档必须带告警 |
| 8 | 申报表落库（销售额 / 销项税 / 附加税费） |
| 9 | 期间格式校验与中文错误提示 |
| 10 | 发票识别链路未被破坏（回归） |
| 11 | ★ **报表绝不产生任何凭证** |
| 12 | 档案删除 |

## 税务填报

位置：**税务填报**（`/tax`）。

### 出的是「底稿」，不是申报

全国统一规范电子税务局目前不提供通用文件导入接口给普通企业，所以本系统产出的是
**与税局表格逐格对照的底稿**：行次排好、每一格标明数据来源，照着填即可。

| 周期 | 产出 |
|---|---|
| 月度 | 资产负债表（会小企01表）· 利润表（会小企02表）· 增值税及附加税费申报底稿 |
| 季度末月（3/6/9/12） | 再加 企业所得税季度预缴底稿 |
| 12 月 | 再加 企业所得税年度汇算清缴底稿 |

### 报表怎么取数：按科目标记归集，不硬编码

科目表 123 个科目**全部**带 `reportItem` 标记，所以报表纯粹按标记归集：

- 同一标记下的多个科目自动合并（`1001+1002+1012 → 货币资金`）
- 调整科目口径只改一处，代码不用动
- **每一行都能追到科目**：界面上点开任意一行，能看到它由哪些科目的余额加总而成

### 三个不能踩的坑（都踩过并修了）

**坑 1：备抵科目与主科目打了同一个标记。**
`1602 累计折旧` 原先与 `1601 固定资产` 共用 `BS_FIXED_ASSET` —— 两者会被**直接相加**，
固定资产虚增一个折旧额，而报表看起来完全正常。`1702 累计摊销`、`1604/1605` 同理。
已拆开标记，并且加了**标记完整性自检**：定义引用的标记在科目表里不存在就报出来，
绝不让它静静变成一行 0。

**坑 2：损益类用余额取数。**
损益类科目期末结转到本年利润后余额为 0，用余额取数会得到一张**全 0 的利润表**。
利润表必须用**本期发生额**。

**坑 3：「减：累计折旧」被当成合计行丢掉。**
报表识别那侧踩过同一个坑（见「报表读取」一节）。报表里的「减：」只是列示前缀，
指向的是独立科目，不是合计行。

### 该判断的留空，不代填

这是本模块最重要的设计决定。企业所得税的口径大量依赖判断，
**自动算出来的调整额如果错了，用户会直接照着申报 —— 那比不给结果更糟**。

| 项目 | 处理 |
|---|---|
| 利润总额、应纳所得税额、附加税费 | 按税法规定直接算 |
| 纳税调整增加/减少额 | **留空**，列出线索与扣除限额依据 |
| 年度汇算的税率 | **留空**（应纳税所得额还没算出来，预填一个 25% 会被当成结论照抄） |
| 小型微利企业资格 | 标 `UNKNOWN` —— 三项条件系统只算得出一项（另两项是从业人数与资产总额） |
| 资产负债表不平衡 | 报出差额，**绝不自动抹平** |

界面上「需人工判断」的格子显示为红色的"待判断"，而不是 0 ——
0 会被误读成"这项没有"。

### 附加税费

计税依据是**本期实际应缴纳的增值税**（不是销项税额，也不是利润）。
城建税税率按纳税人所在地分档（市区 7% / 县镇 5% / 其他 1%），界面上可选；
教育费附加 3%、地方教育附加 2% 为常见口径，可通过参数覆盖。

### 时效性

税率与优惠门槛会变。代码里是**默认值**，政策变动由「税务政策检索」负责发现并提示。

## 税务政策检索

### 这个模块不做什么

先说清楚，因为它最容易被误解：

- ✗ 不判断某条政策是否**适用于你**
- ✗ 不替你决定申报口径
- ✗ 不保证搜到的就是全部（只覆盖已登记的来源）
- ✗ 不把政策的"解读"当结论

### 它做什么

按月检索**官方来源**（财政部、国家税务总局、省税务局 —— 不登记任何第三方解读站点），
把每一条政策的这些信息存下来：

```
原文正文 · 发文机关 · 文号 · 发文日期
施行日期 · 失效日期 · 来源链接 · ★ 抓取时间 · 内容哈希
```

**为什么坚持存正文原文**：政策的适用往往取决于**限定条件**
（"……的企业，同时符合下列条件的……"）。如果只给一句"某政策可减半征收"，
用户很可能在不符合条件的情况下照做。所以系统还把
**「同时符合下列条件」这类句子单独摘出来**放在列表里显眼的位置 ——
这是用户最容易忽略、也最容易出错的地方。

**为什么必须存抓取时间**：政策会改，同一个链接在不同时间看到的内容可能不同。
没有抓取时间，事后无法判断"当时看到的是哪一版"。

### 三条防"假成功"的设计

| 问题 | 处理 |
|---|---|
| 抓取全挂了，却报"本期无新政策" | 每次执行都留痕（含失败）。状态分 `SUCCESS / PARTIAL / FAILED`，界面上明确区分"没有新政策"与"抓取失败" |
| 政策被修订，但链接没变、标题没变 | 用内容哈希比对，**变更单独报出来** —— 这类最容易漏 |
| 状态被读成"可以适用" | 措辞统一为「按公布日期推算：已施行」，不是「现行有效，你可以适用」 |

### 调度

每月自动检索一次。**幂等靠查库而不是内存标志**：
每天检查一次「本月是否已有成功记录」，没有就跑。
这样进程重启、机器休眠、手动跑过，都不会导致重复或漏跑。

★ 只有 `SUCCESS / PARTIAL` 算"本月跑过了"。全 `FAILED` 不算 ——
否则一次网络抖动就会让这个月彻底没有政策数据，而这种"静默缺失"没人会发现。

可用环境变量关闭：`TAX_POLICY_SCHEDULE=off`。

### 关于"选择最优方式"

系统**不做**这件事。不是技术做不到，而是判断某个安排是否构成"合理商业目的"、
某项优惠能否适用，属于涉税专业判断，做错了后果是补税加滞纳金。
让软件替用户下这个结论并引导申报，是在替用户承担它承担不起的责任。

系统能做的是把**不同口径下的税额差异算出来供比较**，决策与签字必须是人。

### 抓取器

抓取器是**可注入**的，默认使用内置政策目录（离线可用、结果确定），
接入真实 HTTP 抓取器后可自动获取。这样设计的原因：
① 内网/离线环境也要能用；② 抓取失败必须能被看见，而不是静默返回空。

内置目录是**示例基线**，不保证时效，界面会标注"需以官方来源为准"。

## 报销合规自检

### 边界

**这不是税务意见，也不是审计结论。** 它只做机械核查。
声明会随每次结果一起返回，界面上置顶显示。

### 两类结论，界面分开呈现

**「数据矛盾」** —— 数据本身就能证明有问题，必然有一处是错的：

| 规则 | 说明 |
|---|---|
| `DUP-001` | 同一张发票被**多张凭证**引用（同一张票只能报销一次） |
| `DATE-001` | 凭证日期不在所属会计期间内 |
| `AMT-002` | 凭证金额与所关联发票金额不一致（容差 2 分） |

**「形态可疑」** —— 可能是正常业务，只提示，**绝不说成"违规"**：

| 规则 | 说明 |
|---|---|
| `SEQ-001` | 同一供应商连号发票 —— 连号本身不是问题，一次采购开多张也会连号 |
| `AMT-001` | 大额整数金额（真实交易金额很少正好整千） |
| `DATE-002` | 周末的业务招待费 —— 周末招待客户完全正常 |
| `CP-001` | 同一供应商高频小额（笔数多但单笔金额大的不报） |
| `LIM-001` | 业务招待费超**内部**限额（未配置限额则不检查，避免无意义告警） |
| `CMP-002` | 费用凭证没有原始单据（提示汇算时可能需纳税调增） |
| `CMP-001` | 有发票未关联到任何凭证 |

### 每条结论都带「怎么核实」

只说"有问题"而不说"该怎么查"等于没说。所以每条结论都有四段：
**哪里不对 · 该怎么核实 · 规则依据 · 涉及的具体凭证/发票**。

### 规则的写法原则：宁可漏报，不可误报

一条误报会让人对整个自检失去信任，之后真问题也不会看。
所以每条规则都有一个"必须命中"的用例，和一个"必须不命中"的反例 ——
反例写不出来，说明规则边界没想清楚。31 项单元测试逐条钉住了这个边界。

## 凭证驳回

审核与过账是两个人、两个时间点做的事，后一个人发现问题时必须能退回去。

| 动作 | 状态变化 | 退回到这里的理由 |
|---|---|---|
| 审核不通过 | 待审核 → **草稿** | 单据要改，退回制单人 |
| 退回审核 | 已审核 → **待审核** | 审核那步看漏了，该让审核人重新看，不必让制单人从头再来 |
| 退回制单人 | 已审核 → **草稿** | 单据本身要改，不只是重审 |

三条路径的**理由都必填**，并写入凭证备注**回显给被退回的人** ——
被退了却不知道要改什么，流程就卡住了。理由同时进审计日志（可追溯是谁、因为什么退回）。

★ **已过账的凭证三条路径全部封死**。已过账的账只能红冲，不能改 ——
这是「已结账的账改不动」这条红线的具体落点。

### 修过的两个缺陷

**`rejectAfterReview` 在草稿上会被静默执行。** 因为 `DRAFT → REVIEWING` 本来就是合法的
「提交审核」，于是"退回审核"退化成了一次无意义的状态回写。
修法：给 `assertTransition` 加了**来源状态**约束 ——
每个动作必须从它语义上该有的状态出发，不靠调用方自觉。

**同一期间只能存在一张草稿凭证。** `voucherNo` 的唯一约束把"未编号"的 `0`
当成了真实凭证号，第二张草稿直接撞唯一约束报 500。
改用部分唯一索引（只对 `voucherNo > 0` 生效），凭证号唯一性一点没削弱。

## 识别目标自动判定

位置：**录入凭证 → 识别录入**（`/vouchers/recognition`）。

### 解决的什么问题

上传一个文件时，用户不该先想清楚"这是发票还是报表"。
系统应该自己看出来 —— **实在看不出来，再问人**。

判错的后果不是"多一步确认"，而是**数据进错识别管道**：
把资产负债表当发票识别，AI 会被要求从表里抽「发票号码」，
抽不出来还硬抽，最后可能生成一张完全错误的记录并落库。
所以这里的默认值是「自动判定 + 可覆盖」，而不是「先让用户选」。

### 判定依据分三层，从强到弱

| 层级 | 信号 | 例子 |
|---|---|---|
| ① 文件类型 | 扩展名 | `.xlsx`/`.csv` → 报表或台账，不可能是发票扫描件 |
| ② 标题 | 表单类文档第一行就是它的名字 | 「资产负债表」「增值税及附加税费申报表」 |
| ③ 字段结构 | 有「发票号码」就是发票，有「期末余额/年初余额」就是报表 | — |

三层都不命中 → 返回 `needsTargetChoice`，**不执行识别**，把选择权交回去。

### 覆盖的单据类型

| 类型 | 识别目标 | 说明 |
|---|---|---|
| 增值税发票 | `INVOICE` | 单张票 |
| 银行回单 | `BANK_SLIP` | 单笔收付款 |
| 银行流水 | `BANK_STATEMENT` | 整月多笔 |
| 资产负债表 / 利润表 | `BALANCE_SHEET` / `INCOME_STATEMENT` | 只建档 |
| 纳税申报表 | `TAX_RETURN` | 增值税 / 企业所得税 |
| 合同 | — | ★ 只作辅助备查，**不参与记账** |
| 收据 | — | 提示税前扣除风险 |
| 发票明细台账 | — | ★ 指引到「历史数据导入」 |

### 三个必须判对的易混淆组合

**① 企业所得税年报 ≠ 利润表。**
所得税年度申报表里也有「营业收入」「利润总额」，先判财务报表就会误判。
所以**先判申报表再判财务报表**，且用「应纳税所得额 / 纳税调整」这类
申报表**独有**的行次做区分。

**② 发票台账 ≠ 单张发票。**
两者都含「发票号码」字段，但台账是一行一张票 ——
拿单张票识别去跑台账只会认出第一张。
判据是**数据行数**：多行 → 台账，单行 → 单张票。

**③ 银行流水常以 Excel 导出。**
如果先按「表格 → 报表」走，流水会被判成未知类型。
所以银行类判定必须**在文件类型分支之前**。
合同与收据同理（合同台账、收据 CSV 都很常见）。

### 判不出来时不猜

纯图片（无文本层）无法在识别之前判断它是什么。这时系统：

- 返回 `needsTargetChoice: true`，**不执行识别**（`preview` 为 `null`）
- 置信度报 `0`，不装出有把握
- 列出可选目标，并说明**为什么**要你选：
  「选错会让数据进错管道 —— 例如把资产负债表当发票识别」

### 人工指定优先

传了 `targetType` 就以你的选择为准，并把 `chosenBy` 标为 `USER`。
若与系统判定不一致，`conflictsWithUserChoice` 为 `true`，界面会提示
「以你的选择为准 —— 但若不确定，建议改用系统判定」。

界面上还有「交回系统自动判定」按钮，可以撤销自己的选择。

### 判定结果与依据一并返回

```jsonc
"classification": {
  "label": "资产负债表",
  "targetType": "BALANCE_SHEET",
  "confidence": 0.95,
  "needsConfirmation": false,
  "evidence": [
    { "signal": "文件是表格格式（.csv），这类文件通常是财务报表或明细台账", "strength": "FILE_TYPE" },
    { "signal": "标题含「资产负债表」", "strength": "TITLE" },
    { "signal": "含「期末余额 / 年初余额 / 资产总计」等报表列", "strength": "FIELD" }
  ],
  "reason": "按文件格式与内容判定为资产负债表，将走报表识别（★ 只建档，不生成凭证）。",
  "chosenBy": "SYSTEM",
  "conflictsWithUserChoice": false
}
```

判错时用户能立刻看出是**哪一步**出的问题，而不是只看到一个错误结果。
